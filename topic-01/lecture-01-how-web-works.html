Вступ до клієнтських технологій

Як браузер і сервер обмінюються даними, як із байтів HTML з'являється сторінка, хто пише правила для всіх браузерів і з якими інструментами ви працюватимете весь курс.

Після лекції ви зможете

  • пояснити архітектуру «клієнт–сервер» і пройти весь життєвий цикл запиту: URL, DNS, з'єднання, HTTP-запит і відповідь, кешування, перенаправлення;
  • розрізняти HTTP і HTTPS: що шифрує TLS, що залишається видимим і навіщо сертифікат;
  • описати, як браузер будує сторінку: парсинг, DOM, CSSOM, дерево рендерингу, layout і paint;
  • пояснити, хто створює стандарти вебу (W3C, WHATWG, Ecma TC39) і як перевірити, чи можна вже використовувати нову можливість;
  • підготувати робоче середовище: VS Code або WebStorm, Node.js LTS і npm, DevTools і Git з осмисленими комітами.

Теорія

Наскрізний приклад лекції — невеликий каталог книжок: сторінка зі списком книжок, пошуком за назвою та обкладинками. На ньому розберемо і мережу, і браузер, і інструменти.

Клієнт і сервер

Коли ви відкриваєте каталог книжок, здається, що сторінка «живе» у вкладці браузера. Насправді HTML-файл, стилі, скрипти й обкладинки лежать на іншому комп'ютері, іноді за тисячі кілометрів. Проблема, яку розв'язує веб, — як мільйонам людей одночасно отримати актуальну версію тих самих файлів, якщо зберігаються вони в одному місці й оновлюються там само.

Відповідь — модель клієнт–сервер. Клієнт — програма, яка ініціює обмін: браузер, мобільний застосунок, утиліта командного рядка. Сервер — програма, яка чекає на запити й відповідає на них. Важливо, що роль визначається тим, хто починає розмову, а не «залізом»: коли ви запускаєте на ноутбуці локальний сервер для розробки, той самий ноутбук одночасно і сервер (програма віддає файли), і клієнт (браузер їх запитує).

Між клієнтом і сервером працює стек протоколів, і кожен шар відповідає за своє. IP доставляє пакети даних за адресою, TCP (або QUIC у HTTP/3) стежить, щоб пакети не губилися й приходили в правильному порядку, а HTTP описує зміст розмови: «дай мені цей ресурс» і «ось він». Наша дисципліна — про клієнтський бік: HTML описує структуру й зміст сторінки, CSS — її вигляд, JavaScript (а згодом TypeScript, що компілюється в JavaScript) — поведінку, а Web API браузера дають коду доступ до DOM, мережі та сховищ. Усе це браузер отримує від сервера й виконує на комп'ютері користувача.

Коли це знадобиться. Щойно щось не працює, перше запитання — на чиєму боці проблема. Помилка в JavaScript видна в консолі браузера й виправляється в клієнтському коді; статус 500 у панелі Network означає, що впав сервер, і правити клієнтський код марно.

Стандарти вебу: W3C, WHATWG, ECMAScript

Каталог книжок має однаково виглядати й працювати в Chrome, Edge, Firefox і Safari. Це продукти різних компаній на різних рушіях: Blink, Gecko, WebKit. Без спільних правил кожен браузер трактував би розмітку по-своєму. Так і було наприкінці 1990-х, у часи «війн браузерів», коли сайти чесно писали «найкраще переглядати в такому-то браузері», а розробники підтримували кілька версій однієї сторінки.

Розв'язання — стандарти: специфікації, які описують поведінку настільки точно, що незалежні реалізації дають однаковий результат. Специфікація HTML, наприклад, визначає не лише теги, а й алгоритм парсингу аж до того, як виправляти помилки в розмітці. Саме тому однаково «зламаний» HTML усі сучасні браузери перетворюють на однаковий DOM. Для клієнтських технологій важливі три організації.

W3C (World Wide Web Consortium) заснований 1994 року творцем вебу Тімом Бернерсом-Лі. Тут розробляють CSS: CSS Working Group видає специфікацію модулями, і кожен модуль розвивається окремо, тому «CSS3» як єдиної версії не існує. Тут же створено настанови доступності WCAG і чимало програмних інтерфейсів браузера.

WHATWG (Web Hypertext Application Technology Working Group) створили 2004 року розробники Apple, Mozilla та Opera, а сьогодні в його керівному комітеті Apple, Google, Microsoft і Mozilla. WHATWG веде HTML, DOM, URL, Fetch, Encoding та інші специфікації як Living Standard: одну безперервно оновлювану версію замість нумерованих випусків. З 2019 року за угодою між W3C і WHATWG єдину версію HTML і DOM розвиває WHATWG. Тому слово «HTML5» сьогодні означає просто HTML.

Ecma International через технічний комітет TC39 розвиває стандарт ECMA-262, тобто ECMAScript. Це специфікація мови, а JavaScript — її реалізація в браузерах і Node.js. З 2015 року видання виходять щороку в червні. ECMAScript 2026, 17-те видання, Генеральна асамблея Ecma затвердила 30 червня 2026 року, а чернетка наступного вже публікується на tc39.es. Нові можливості проходять стадії пропозицій. На Stage 3 специфікація вважається готовою, і браузери починають її реалізовувати. Stage 4 означає, що є сумісні реалізації й тести, і пропозиція потрапить до найближчого щорічного видання.

Важливо розуміти межу. ECMAScript описує саму мову: змінні, функції, об'єкти, масиви, проміси, модулі. А document, fetch, console чи localStorage — це Web API, описані специфікаціями WHATWG і W3C. Браузер надає їх «навколо» мови, а Node.js натомість має власні API, наприклад модуль fs для роботи з файлами.

// ECMAScript: the language itself, works in browsers and in Node.js
function getTitles(books) {
  return books.map((book) => book.title);
}

// Web APIs: provided by the browser, not by the language
function renderTitles(titles) {
  const list = document.querySelector(".book-list"); // DOM Standard (WHATWG)
  list.replaceChildren(...titles.map((title) => {
    const item = document.createElement("li");
    item.textContent = title;
    return item;
  }));
  return list.children.length;
}

Стандарт ще не означає підтримку. Браузери реалізують специфікації у власному темпі, тому перед використанням нової можливості дивляться таблицю Browser compatibility на MDN або позначку Baseline. Статус «Newly available» означає, що можливість уже є в усіх основних браузерах: Chrome, Edge, Firefox і Safari, на комп'ютерах і мобільних. «Widely available» з'являється через 30 місяців після цього, коли старі версії браузерів практично зникли.

Коли це знадобиться. Щоразу, коли треба з'ясувати, як щось працює насправді: першоджерело — специфікація та MDN, а не стаття десятирічної давнини. І щоразу, коли вирішуєте, чи можна вже використати нову можливість CSS чи JavaScript у проєкті.

Анатомія URL

Щоб отримати ресурс, клієнт має однозначно сказати, що саме й де його взяти. Для цього існує URL (Uniform Resource Locator) — рядок, який браузер розбирає за правилами стандарту WHATWG URL. Кожна частина адреси має свого «читача», і розуміння цього пояснює безліч дивних на перший погляд ситуацій.

Схема (https:) визначає протокол. Хост (books.example.com) — ім'я сервера, яке ще треба перетворити на IP-адресу через DNS. Порт — номер «дверей» на сервері; якщо його не вказано, браузер бере типовий: 80 для http і 443 для https. Шлях (/catalog/search) каже серверу, який ресурс потрібен. Рядок запиту (?q=css&page=2) передає параметри парами ключ=значення, розділеними &. Фрагмент (#results) взагалі не надсилається на сервер: браузер використовує його сам, щоб прокрутити сторінку до елемента з id="results".

У URL дозволено лише обмежений набір символів ASCII, тому пробіли, кирилиця та спецсимволи кодуються відсотками: пробіл стає %20, а слово «книга» перетворюється на %D0%BA%D0%BD%D0%B8%D0%B3%D0%B0 — це байти UTF-8. Браузер показує вам гарну адресу в рядку, але по мережі йде закодований варіант.

У JavaScript розбирати адреси вручну через split не потрібно: вбудований клас URL робить це за стандартом, так само як браузер.

function describeUrl(address) {
  const url = new URL(address);
  return {
    protocol: url.protocol, // "https:"
    hostname: url.hostname, // "books.example.com"
    port: url.port,         // "" — the default port 443 is omitted
    pathname: url.pathname, // "/catalog/search"
    search: url.search,     // "?q=css&page=2"
    hash: url.hash,         // "#results"
  };
}

function getSearchQuery(address) {
  const url = new URL(address);
  return url.searchParams.get("q"); // "css"
}

console.log(describeUrl("https://books.example.com:443/catalog/search?q=css&page=2#results"));
console.log(getSearchQuery("https://books.example.com/catalog/search?q=css"));

Ще одне поняття, яке знадобиться вже на цьому занятті, — походження (origin): комбінація схеми, хоста й порту. Адреси http://127.0.0.1:5500 і http://127.0.0.1:3000 мають різне походження, хоча це той самий комп'ютер. Браузер застосовує правила безпеки саме на рівні походження, і сторінка, відкрита з диска через file://, отримує «порожнє» походження null — про наслідки поговоримо в розділі про VS Code.

Посилання в HTML часто бувають відносними: css/main.css, ../img/cover.png. Браузер перетворює їх на абсолютні відносно адреси поточного документа, відкидаючи ім'я файлу й застосовуючи .. як «на рівень вище».

Коли це знадобиться. Коли потрібно прочитати параметри пошуку чи фільтра з адреси сторінки, зрозуміти, чому зображення з відносним шляхом не знаходиться, або пояснити, чому зміна #фрагмента не перезавантажує сторінку.

DNS на рівні ідеї

Мережа маршрутизує пакети за IP-адресами на кшталт 203.0.113.10 (IPv4) чи 2001:db8::10 (IPv6), а люди запам'ятовують імена. До того ж IP-адреса сервера може змінитися, а одне ім'я — вказувати на кілька серверів у різних країнах. Тому ім'я й адреса мають бути розв'язані одне від одного.

Цю задачу розв'язує DNS (Domain Name System) — розподілена «телефонна книга» інтернету. Браузер через операційну систему питає резолвер (зазвичай сервер провайдера або публічний DNS): «яка адреса в books.example.com?». Якщо відповіді немає в кеші, резолвер іде ієрархією: кореневі сервери підкажуть, хто відповідає за зону .com, ті — хто авторитетний для example.com, а авторитетний сервер поверне запис: A для IPv4 або AAAA для IPv6.

Кожна відповідь має TTL (time to live) — скільки секунд її можна тримати в кеші. Кешують і браузер, і операційна система, і резолвер, тому повторні відвідування сайту обходяться майже без DNS-запитів. Звідси й типовий ефект: після зміни DNS-записів частина користувачів якийсь час бачить старий сервер, доки не мине TTL. Ім'я localhost узагалі не йде в DNS — система одразу розв'язує його в 127.0.0.1.

Коли це знадобиться. Помилка на кшталт «не вдалося знайти IP-адресу сервера» — це DNS, а не ваш код. Також DNS пояснює, чому перше відкриття нового сайту трохи повільніше за наступні.

HTTP: запит і відповідь

Знаючи IP-адресу, браузер встановлює з'єднання і має якось сказати серверу, чого хоче. Потрібна спільна мова, зрозуміла будь-якому браузеру й будь-якому серверу, — це HTTP (HyperText Transfer Protocol). Він побудований як обмін повідомленнями: клієнт надсилає запит, сервер повертає відповідь. Запит складається з рядка запиту (метод, шлях, версія протоколу), заголовків і, за потреби, тіла.

GET /catalog/search?q=css&page=2 HTTP/1.1
Host: books.example.com
Accept: text/html
Accept-Language: uk,en;q=0.8
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)

Зверніть увагу: у запиті немає фрагмента #results, а ім'я хоста йде окремим заголовком Host, бо на одному IP можуть жити сотні сайтів. Метод описує намір: GET — отримати ресурс (саме його надсилає браузер, коли ви вводите адресу), POST — передати дані на обробку, наприклад, відправити форму. Відповідь має схожу будову: рядок статусу, заголовки й тіло.

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 5123
Cache-Control: max-age=600

<!doctype html>
<html lang="uk">
  ...

Статус-код — тризначне число, перша цифра якого задає клас: 2xx — успіх (200 OK, 201 Created), 3xx — перенаправлення або «бери з кешу» (301 Moved Permanently, 304 Not Modified), 4xx — помилка клієнта (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found), 5xx — помилка сервера (500 Internal Server Error, 503 Service Unavailable). Заголовок Content-Type вирішальний: саме за ним, а не за розширенням файлу, браузер вирішує, як інтерпретувати тіло — як HTML, CSS, JavaScript чи зображення.

HTTP не зберігає стан між запитами: кожен запит самодостатній, і сервер «не пам'ятає», що ви щойно завантажували. Стан (наприклад, те, що ви увійшли в обліковий запис) передається явно — через cookie чи заголовки. Крім того, кожен ресурс — окремий запит: сторінка каталогу з одним CSS, двома скриптами й двадцятьма обкладинками — це понад двадцять запитів, і всі вони видні в DevTools.

Версії HTTP/2 і HTTP/3 змінили транспорт (кілька запитів в одному з'єднанні, протокол QUIC), але зміст — методи, статуси, заголовки — лишився тим самим. У DevTools для HTTP/2 ви побачите псевдозаголовки :method і :path замість рядка запиту — це ті самі дані в іншому записі.

Коли це знадобиться. Постійно: коли стилі «не підтягнулися» (шукайте 404 на CSS-файлі), коли сервер повертає 500, коли браузер показує JavaScript-файл як текст (неправильний Content-Type), і в наступних лекціях про роботу з API через fetch.

HTTPS і TLS

HTTP-повідомлення від браузера до сервера проходять через десяток чужих вузлів: роутер кав'ярні, мережу провайдера, магістральні канали. У звичайному HTTP усе передається відкритим текстом. Будь-хто на шляху може прочитати пароль чи cookie, непомітно змінити відповідь, наприклад вставити в сторінку рекламу чи шкідливий скрипт, або видати себе за сервер.

HTTPS — це той самий HTTP, але поверх протоколу TLS (сучасна версія — TLS 1.3). TLS дає три гарантії. Перша — конфіденційність: дані зашифровано. Друга — цілісність: будь-яку зміну дорогою буде виявлено. Третя — автентичність: ви говорите саме з books.example.com, а не з підмінним сервером.

Автентичність забезпечує сертифікат. Це документ, який пов'язує доменне ім'я з публічним ключем сервера і підписаний центром сертифікації (CA). Під час TLS-рукостискання сервер надсилає сертифікат, а браузер перевіряє три речі. Перша — ланцюжок підписів веде до кореневого сертифіката з довіреного сховища системи чи браузера. Друга — ім'я в сертифікаті збігається з хостом. Третя — термін дії не минув. Якщо хоч одна перевірка не проходить, браузер показує повноекранне попередження замість сайту. Потім сторони узгоджують одноразові симетричні ключі сесії, і далі шифрується все HTTP-повідомлення: рядок запиту зі шляхом і параметрами, заголовки, cookie, тіло.

Водночас HTTPS не приховує всього. Сторонній спостерігач бачить IP-адресу сервера, ім'я хоста (з DNS-запиту та поля SNI в рукостисканні), обсяг і час передачі. А секрети в URL небезпечні й без перехоплення, бо адреса зберігається в історії браузера та журналах сервера.

Кілька механізмів підтримують HTTPS на практиці. Сервер перенаправляє запити з http:// на https:// статусом 301 або 308. Заголовок Strict-Transport-Security (HSTS) наказує браузеру надалі відкривати домен лише через HTTPS, навіть якщо користувач ввів http://. Якщо сторінка на HTTPS підключає скрипт через http:// (mixed content), браузер такий ресурс блокує, бо він зруйнував би захист усієї сторінки. Нарешті, частина Web API доступна лише в безпечному контексті (secure context): геолокація, Service Worker, Clipboard API. Безпечним вважається HTTPS, а також localhost і 127.0.0.1, тому під час розробки на Live Server ці API працюють і без сертифіката.

GET /catalog HTTP/1.1
Host: books.example.com

HTTP/1.1 301 Moved Permanently
Location: https://books.example.com/catalog

HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Type: text/html; charset=utf-8

Коли це знадобиться. Коли сторінка показує попередження про сертифікат, коли в консолі з'являється помилка Mixed Content, коли API на кшталт геолокації «не працює» на відкритій через IP адресі, і коли вирішуєте, які дані взагалі можна передавати в URL.

Життєвий цикл запиту

Окремі частини ми вже розібрали: URL, DNS, HTTP, TLS. Тепер зберемо їх у повний цикл одного запиту. Важливо пам'ятати, що одна сторінка — це десятки таких циклів: документ, кожен CSS-файл, скрипт, шрифт, зображення. Кожен запит проходить свій шлях, і на кожному кроці браузер намагається зекономити час.

Цикл починається з формування абсолютного URL: відносний шлях на кшталт css/main.css розв'язується відносно адреси документа. Далі браузер перевіряє HTTP-кеш. Якщо збережена копія ще свіжа (сервер дозволив це заголовком Cache-Control: max-age=600), запит у мережу взагалі не йде, і в Network видно «(memory cache)» або «(disk cache)». Якщо копія застаріла, але має мітку версії ETag, браузер надсилає умовний запит. Сервер, переконавшись, що файл не змінився, відповідає коротким 304 Not Modified без тіла, і браузер бере тіло з кешу.

GET /css/main.css HTTP/1.1
Host: books.example.com
If-None-Match: "a1b2c3"

HTTP/1.1 304 Not Modified
ETag: "a1b2c3"
Cache-Control: max-age=600

Якщо мережа таки потрібна, браузер розв'язує ім'я через DNS (теж з кешем) і встановлює з'єднання. Для HTTPS до цього додається ще TLS-рукостискання. Вже відкрите з'єднання з тим самим сервером використовується повторно, а HTTP/2 і HTTP/3 передають кілька запитів одним з'єднанням паралельно. Потім іде запит: рядок запиту, заголовки й cookie, які сервер раніше встановив заголовком Set-Cookie. Сервер обробляє запит і повертає відповідь. Статус 3xx із заголовком Location запускає новий цикл за новою адресою, і в Network такий ланцюжок видно повністю. Статус 2xx означає, що тіло обробляється відповідно до Content-Type.

Для HTML-документа цикл не закінчується на відповіді. Парсер знаходить підресурси й породжує нові запити. Сторінка проходить дві ключові події: DOMContentLoaded настає, коли DOM побудовано й виконано скрипти з defer, а load — коли завантажено все, включно із зображеннями й шрифтами.

function formatPageEvent(eventName) {
  const elapsed = Math.round(performance.now());
  return `${eventName}: ${elapsed} ms after navigation start`;
}

document.addEventListener("DOMContentLoaded", () => {
  console.log(formatPageEvent("DOMContentLoaded"));
});

window.addEventListener("load", () => {
  console.log(formatPageEvent("load"));
});

Коли це знадобиться. Вкладка Timing будь-якого запиту в панелі Network — це і є життєвий цикл у мілісекундах: DNS Lookup, Initial connection, SSL, Waiting for server response, Content Download. Коли сторінка вантажиться повільно, саме тут видно, на якому кроці втрачається час. Пройти цикл крок за кроком можна в інтерактивному демо.

Як браузер будує сторінку: DOM, CSSOM, рендеринг

Сервер повернув байти HTML. Але байти — не сторінка: браузер має зрозуміти структуру документа, застосувати стилі, виконати скрипти й перетворити все це на пікселі. І робити це треба швидко, не чекаючи, поки завантажиться кожна обкладинка.

Спершу парсер HTML декодує байти в символи (за charset), розбиває їх на токени — теги, атрибути, текст — і будує з них дерево об'єктів, DOM (Document Object Model). Парсер HTML навмисно поблажливий: незакриті теги він закриває, пропущені обов'язкові елементи додає. Тому DOM може відрізнятися від вашого вихідного файлу — наприклад, у <table> з'являється <tbody>, якого ви не писали. Натрапивши на <link rel="stylesheet">, <img> чи <script src>, браузер ставить у чергу нові HTTP-запити, не зупиняючи розбір.

Паралельно CSS перетворюється на CSSOM — дерево правил зі всіма каскадами й успадкуванням. CSS блокує рендеринг: поки таблиці стилів із <head> не завантажені, браузер нічого не малює, бо інакше користувач побачив би голу розмітку, яка за мить «перестрибне» в оформлену сторінку.

Найцікавіше — JavaScript. Звичайний <script src="..."> без атрибутів блокує парсер: розбір HTML зупиняється, скрипт завантажується й виконується, і лише потім парсер іде далі. Так історично склалося, бо скрипт може змінити документ ще під час розбору. Наслідок: скрипт у <head> не бачить елементів, які йдуть нижче, — їх ще немає в DOM, і document.querySelector повертає null. Атрибут defer розв'язує проблему: скрипт завантажується паралельно з розбором, а виконується після того, як DOM повністю побудовано, у порядку підключення. Атрибут async виконує скрипт одразу після завантаження, без гарантії порядку, — він для незалежних скриптів на кшталт аналітики. Модулі (type="module") за замовчуванням поводяться як defer.

<!doctype html>
<html lang="uk">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Book catalog</title>
    <link rel="stylesheet" href="css/main.css">
    <script src="js/app.js" defer></script>
  </head>
  <body>
    <h1>Book catalog</h1>
    <ul class="book-list"></ul>
  </body>
</html>

Коли DOM і CSSOM готові, браузер об'єднує їх у дерево рендерингу — лише видимі вузли з обчисленими стилями (елементи з display: none туди не потрапляють, а от visibility: hidden займає місце й потрапляє). Далі йде layout (компонування): для кожного блоку обчислюються розмір і позиція з урахуванням ширини вікна. Потім paint — малювання пікселів: тексту, кольорів, рамок, тіней — і composite, коли намальовані шари складаються в кінцеве зображення на екрані.

Цей конвеєр не одноразовий. Кожна зміна DOM чи стилів з JavaScript може знову запустити частину кроків: зміна кольору вимагає лише перемалювання, а зміна ширини — повторного layout для елемента й усього, що від нього залежить. Тому розуміння конвеєра — основа продуктивності фронтенду.

Коли це знадобиться. Коли вирішуєте, куди й як підключати скрипти (відповідь за замовчуванням — defer у <head> або модуль), коли в Elements бачите не те, що написали, і коли сторінка «блимає» без стилів.

Редактор коду: VS Code і WebStorm

Писати HTML і CSS можна й у «Блокноті», але тоді ви вручну закриваєте кожен тег, шукаєте пропущену дужку очима й сперечаєтеся з колегами про відступи. Редактор коду бере цю рутину на себе: підсвічує синтаксис, доповнює код, показує помилки до запуску, форматує й інтегрується з Git і терміналом. У курсі можна працювати в одному з двох інструментів, і їхні можливості для верстки та JavaScript перетинаються майже повністю.

Visual Studio Code — безкоштовний редактор від Microsoft. З коробки він підтримує HTML, CSS, JavaScript і TypeScript, а решту можливостей додають розширення з панелі Extensions (Ctrl+Shift+X, на macOS Cmd+Shift+X). Для курсу знадобляться два: Prettier для автоматичного форматування і Live Server для локального сервера з автоперезавантаженням. Будь-яку команду можна знайти через палітру команд Ctrl+Shift+P.

WebStorm — повноцінне середовище розробки (IDE) від JetBrains, спеціалізоване на JavaScript і TypeScript. Те, що у VS Code додається розширеннями, тут є одразу: глибокий аналіз коду, безпечні рефакторинги, налагоджувач, запуск тестів, інтерфейс для Git, вбудований вебсервер, інтеграція з Prettier. З жовтня 2024 року WebStorm безкоштовний для некомерційного використання, зокрема навчання: під час першого запуску достатньо вибрати ліцензію Non-commercial use. Пошук будь-якої дії відкривається комбінацією Ctrl+Shift+A (на macOS Cmd+Shift+A).

Emmet вбудований в обидва редактори й розгортає короткі абревіатури в розмітку за клавішею Tab. Знак оклику ! у порожньому HTML-файлі дає повний каркас документа. Синтаксис абревіатур схожий на CSS-селектори: . — клас, # — id, > — вкладений елемент, + — сусідній, *3 — повторити тричі, {} — текст усередині.

ul.book-list>li.book*3>h2.book__title{Title}+p.book__author
<ul class="book-list">
  <li class="book">
    <h2 class="book__title">Title</h2>
    <p class="book__author"></p>
  </li>
  <li class="book">
    <h2 class="book__title">Title</h2>
    <p class="book__author"></p>
  </li>
  <li class="book">
    <h2 class="book__title">Title</h2>
    <p class="book__author"></p>
  </li>
</ul>

Форматування вирівнює відступи, переноси й лапки за єдиними правилами. У VS Code команда Format Document викликається комбінацією Shift+Alt+F у Windows, Shift+Option+F у macOS і Ctrl+Shift+I у Linux. У WebStorm це Reformat Code: Ctrl+Alt+L, на macOS Cmd+Option+L. Значно краще доручити це редактору при кожному збереженні. У WebStorm це налаштовується в Settings → Tools → Actions on Save (Reformat code або Run Prettier), у VS Code — у файлі налаштувань робочої області.

{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.tabSize": 2,
  "files.eol": "\n"
}

Якщо в команді працюють у різних редакторах, правила форматування варто тримати не в налаштуваннях редактора, а у файлі .prettierrc у корені проєкту. Його читають і розширення Prettier у VS Code, і WebStorm, тож код буде відформатовано однаково незалежно від того, хто й де його зберіг.

Локальний сервер. Live Server у VS Code запускає невеликий HTTP-сервер (типово на порту 5500) і відкриває сторінку за адресою на кшталт http://127.0.0.1:5500/index.html; після кожного збереження сторінка перезавантажується. Запускається він кнопкою Go Live у рядку стану або командою Open with Live Server з контекстного меню HTML-файлу. WebStorm має вбудований сервер: коли ви відкриваєте HTML-файл у браузері з редактора, адреса має вигляд http://localhost:63342/book-catalog/index.html, де book-catalog — назва проєкту.

Чому не просто двічі клацнути по файлу? Тоді браузер відкриє його через file://, і сторінка отримає походження null. Для статичного HTML і CSS це непомітно, але модулі JavaScript і запити fetch підпадають під правила CORS, і браузер їх блокує, щоб сторінка з диска не могла читати інші ваші файли. Локальний сервер віддає файли по HTTP так само, як справжній хостинг, тож поведінка під час розробки збігається з поведінкою в інтернеті.

Коли це знадобиться. На кожному занятті. Вибір редактора — справа смаку, а от звички спільні: Emmet для верстки, форматування при збереженні з єдиним .prettierrc і локальний сервер, обов'язковий, щойно в проєкті з'являються модулі чи fetch.

Node.js LTS і npm як інструменти

Prettier, лінтери, компілятор TypeScript, збирачі й сервери для розробки — це програми, написані на JavaScript. Браузер їх не запустить: у сторінки немає доступу до ваших файлів. Потрібне середовище, яке виконує JavaScript на самому комп'ютері. А щоб у всіх учасників проєкту були однакові версії цих інструментів, потрібен ще й менеджер пакетів.

Node.js — середовище виконання JavaScript поза браузером, побудоване на рушії V8, тому самому, що в Chrome. У нашій дисципліні ми не пишемо на Node.js серверний код: він слугує інструментом на вашому комп'ютері, який запускає утиліти для фронтенду. Тут добре видно межу між мовою і платформою. Мова та сама (ECMAScript), але document і window у Node.js немає, натомість є власні модулі, наприклад fs для роботи з файлами.

Для навчання й роботи беруть версію LTS (Long Term Support): вона стабільна й роками отримує виправлення безпеки. Досі нові мажорні версії Node.js виходили двічі на рік, а LTS ставали парні. Станом на початок жовтня 2026 року Active LTS — Node.js 24, а наприкінці жовтня цей статус переходить до Node.js 26. Починаючи з Node.js 27 проєкт переходить на один мажорний випуск на рік: у квітні виходить нова версія, а в жовтні вона стає LTS, і так кожна. Актуальний стан завжди видно на сторінці релізів nodejs.org. Встановлюють Node.js інсталятором LTS з офіційного сайту або менеджером версій, якщо треба тримати кілька версій паралельно.

Разом із Node.js встановлюється npm — менеджер пакетів і найбільший реєстр JavaScript-пакетів. Його центр — файл package.json, «паспорт» проєкту з назвою, скриптами й залежностями. Інструменти розробки записують у devDependencies: вони потрібні вам, але не потрапляють на сторінку в браузері.

# Check the installation
node -v
npm -v

# Create package.json and add Prettier as a dev tool
npm init -y
npm install --save-dev prettier

# Run the locally installed tool
npx prettier --write .

# Run a script defined in package.json
npm run format

# Install exact versions from package-lock.json (fresh clone, CI)
npm ci
{
  "name": "book-catalog",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  },
  "devDependencies": {
    "prettier": "^3.6.2"
  }
}

Версії пакетів записуються за семантичним версіонуванням MAJOR.MINOR.PATCH. Номер у прикладі умовний: npm сам підставить актуальну версію під час встановлення. Префікс ^ дозволяє оновлення в межах тієї самої мажорної версії, бо зміна MAJOR за домовленістю означає несумісні зміни. Щоб не було сюрпризів, npm створює package-lock.json, у якому записано точні версії всього дерева залежностей. Цей файл комітять у Git, а папку node_modules додають у .gitignore: вона відновлюється командою npm ci рівно в тому стані, що зафіксований у lock-файлі.

Чому команда з scripts працює, хоча Prettier не встановлено глобально? Під час npm run npm додає до шляху пошуку програм папку node_modules/.bin проєкту. Утиліта npx робить те саме для разового запуску. Тому кожен проєкт працює зі своєю версією інструмента, а не з тією, що випадково стоїть у системі.

Коли це знадобиться. Уже в цьому курсі: форматування через Prettier, компіляція TypeScript, локальні сервери й збирачі для проєктів з модулями — усе це запускається через Node.js і npm. Звичка «інструменти — у devDependencies, запуск — через npm run» знадобиться в будь-якому сучасному фронтенд-проєкті.

DevTools: Elements, Console, Network, Sources

Сторінка поводиться не так, як ви задумали, а в коді «все правильно». Гадати можна довго, але браузер знає точно, що він отримав, що побудував і де впав. Інструменти розробника (DevTools) показують його внутрішній стан. Відкриваються вони клавішею F12 або Ctrl+Shift+I (на macOS Cmd+Option+I), а також пунктом «Переглянути код» у контекстному меню елемента. Приклади нижче стосуються Chrome, у Firefox і Edge панелі аналогічні.

Elements показує живий DOM — не вихідний файл, а те, що побудував парсер і змінив JavaScript. Праворуч — стилі вибраного елемента з позначкою, яке правило перемогло в каскаді, обчислені значення (Computed) і схема блокової моделі. Будь-що тут можна змінити й одразу побачити результат, але зміни зникнуть після перезавантаження — це полігон для експериментів, а не редактор.

Console показує помилки й попередження з посиланням на файл і рядок, а також виконує JavaScript у контексті сторінки. Для налагодження зручні console.log і console.table, який виводить масив об'єктів таблицею.

const books = [
  { title: "CSS in Depth", author: "Keith Grant", year: 2024 },
  { title: "Eloquent JavaScript", author: "Marijn Haverbeke", year: 2024 },
  { title: "HTML and CSS", author: "Jon Duckett", year: 2011 },
];

function getBooksByTitle(bookList, query) {
  const normalized = query.trim().toLowerCase();
  return bookList.filter((book) => book.title.toLowerCase().includes(normalized));
}

console.table(getBooksByTitle(books, "css"));

Network перелічує кожен HTTP-запит сторінки: метод, статус, тип, розмір, час. Клік по запиту відкриває заголовки, тіло відповіді й хронологію. Фільтри (Fetch/XHR, CSS, JS, Img) звужують список; прапорець Disable cache вимикає HTTP-кеш, поки DevTools відкриті, а Preserve log зберігає список запитів між перезавантаженнями.

Sources — дерево файлів сторінки й налагоджувач. Клік по номеру рядка ставить точку зупинки (breakpoint): коли виконання дійде до неї, код зупиниться, і в панелі Scope видно значення всіх змінних у цей момент. Далі можна виконувати код покроково. Те саме робить інструкція debugger; у коді, якщо DevTools відкриті.

Коли це знадобиться. Щоразу, коли працюєте над сторінкою: Console — щоб одразу бачити помилки, Network — щоб перевірити, що всі файли завантажилися зі статусом 200, Elements — щоб зрозуміти, чому стиль не застосувався, Sources — коли console.log уже не вистачає.

Git: базові команди

Знайомі імена файлів catalog_final.zip, catalog_final_2.zip, catalog_final_REAL.zip? Без системи контролю версій неможливо сказати, що змінилося між версіями, неможливо безпечно повернутися до робочого стану, і вдвох над одним проєктом працювати майже нереально.

Git розв'язує це, зберігаючи історію проєкту як послідовність комітів — знімків усіх відстежуваних файлів з автором, датою, повідомленням і посиланням на попередній коміт. Git розподілений: кожна копія репозиторію містить повну історію, тож працювати можна без інтернету, а GitHub чи інший сервіс — це просто ще одна копія, з якою ви синхронізуєтеся.

Ключ до розуміння Git — три зони. Робоча директорія — файли, які ви редагуєте. Індекс (staging area) — «чернетка» наступного коміту: сюди командою git add ви кладете саме ті зміни, які хочете зафіксувати. Репозиторій — збережені коміти. Коміт фіксує вміст індексу, а не всі змінені файли, і саме тому можна розбити день роботи на кілька логічних комітів. Гілка — рухомий покажчик на коміт; нова гілка дає змогу пробувати зміни, не чіпаючи основну.

# One-time setup
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

# Start a repository and make the first commit
git init
git status
git add index.html css/main.css
git commit -m "Add book catalog page skeleton"

# Inspect history and changes
git log --oneline
git diff            # working tree vs index
git diff --staged   # index vs last commit

# Undo local changes
git restore index.html          # discard unstaged edits
git restore --staged index.html # remove file from the index

# Branches
git switch -c feature/title-search
git switch main

# Work with a remote repository
git remote add origin https://github.com/your-name/book-catalog.git
git push -u origin main
git pull
git clone https://github.com/your-name/book-catalog.git

Команда git status — ваш компас: вона завжди каже, які файли змінені, які в індексі, а які Git не відстежує взагалі. Під час першого git push на GitHub знадобиться автентифікація (через браузер або персональний токен) — пароль від облікового запису для цього не використовується.

Коли це знадобиться. З першого файлу кожної лабораторної. Git — не інструмент «для великих проєктів», а звичка: git init на початку, коміт після кожного логічного кроку, git push наприкінці заняття.

Кожен із цих прийомів «працює» на вашому комп'ютері сьогодні, і саме тому він небезпечний: проблема вилазить пізніше, в іншому браузері, на сервері чи в команді.

Відкривати сторінку через file:// замість локального сервера

✗ Погано 
<!-- Opened by double-click:
     file:///C:/Users/student/Desktop/book-catalog/index.html -->
<script type="module" src="js/app.js"></script>
// js/app.js
import { renderBooks } from "./render.js";

const response = await fetch("data/books.json");
renderBooks(await response.json());

Чому це погано. Сторінка з file:// має походження null. Модулі й fetch перевіряються за правилами CORS, тож браузер блокує їх, щоб довільний HTML-файл не міг читати інші файли на вашому диску. У Console з'являється помилка на кшталт «blocked by CORS policy», каталог порожній, а студент шукає помилку в коді, де її немає. До того ж поведінка з file:// відрізняється між браузерами, тож «у мене працює» нічого не гарантує.

✓ Добре

http://127.0.0.1:5500/index.html

WebStorm → open index.html → Open in Browser
http://localhost:63342/book-catalog/index.html

Ігнорувати помилки в Console

✗ Погано 
// Typo in the selector: ".book-lits"

Чому це погано. querySelector не знайшов елемент і повернув null, виклик append на null кидає TypeError: Cannot read properties of null, і виконання скрипту зупиняється на цьому рядку. Усе, що нижче, — пошук, обробники подій — просто не запускається. Консоль закрита, тож студент бачить лише «пошук не працює» і змінює код навмання, хоча браузер уже вказав файл і рядок.

✓ Добре 
function getBookList() {
  const list = document.querySelector(".book-list");
  if (!list) {
    throw new Error('Element ".book-list" was not found in the DOM');
  }
  return list;
}

getBookList().append(createBookItem(book));
initSearch();

Консоль відкрита під час роботи; повідомлення про помилку читається до кінця, а клік по посиланню app.js:12 веде прямо до рядка в Sources.

Встановлювати інструменти глобально замість devDependencies

✗ Погано

Абсолютні шляхи до файлів на своєму диску

Осмислені повідомлення комітів

Історія комітів читається частіше, ніж пишеться: під час перевірки лабораторної, пошуку, коли щось зламалося, чи повернення до старої версії. Рекомендація Pro Git: короткий підсумок до 50 символів у наказовому способі («Add», а не «Added»), порожній рядок, далі за потреби пояснення — чому зроблено зміну. .gitignore з першого коміту

.gitignore діє лише на файли, які Git ще не відстежує. Якщо створити його після першого git add ., непотрібне вже в історії. Тому файл з'являється в проєкті разом з git init. Шаблони: папка/ — уся папка, *.log — за маскою, ! — виняток із попереднього правила.

# Dependencies
node_modules/

# Environment variables
.env
.env.*

# OS files
.DS_Store
Thumbs.db

# Editors: ignore personal settings, keep shared ones
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
.idea/workspace.xml
.idea/shelf/

# Logs and build output
*.log
dist/

Маленькі коміти з перевіркою перед фіксацією

Один коміт — одна логічна зміна, яку можна описати одним реченням. Перед комітом варто подивитися, що саме потрапить в індекс: так у коміт не просочаться налагоджувальні console.log чи випадкові файли.

git status
git add js/search.js
git diff --staged
git commit -m "Ignore letter case in title search"

Node.js LTS і зафіксовані залежності

LTS-версія Node.js отримує виправлення безпеки роками, а інструменти фронтенду тестуються насамперед на ній. Щоб у всіх учасників проєкту була та сама версія середовища й пакетів, мінімальну версію Node.js вказують у engines, package-lock.json комітять, а залежності встановлюють командою npm ci. Тоді «у мене працює» означає «працює в усіх».

{
  "name": "book-catalog",
  "private": true,
  "engines": {
    "node": ">=24"
  }
}
node -v   # an LTS line, e.g. v24.x
npm ci    # exact versions from package-lock.json

Працювати з відкритими DevTools

Помилка, помічена одразу, коштує секунди; та сама помилка через годину, після десятка інших змін, — годину пошуку. Тримайте відкритими Console і Network, а під час роботи зі стилями й скриптами вмикайте Disable cache, щоб браузер не показував стару версію файлу з кешу.

F12 → Network → [x] Disable cache
F12 → Console → filter: Errors

Підключати скрипти з defer або як модулі

Скрипт у <head> з defer починає завантажуватися якомога раніше, паралельно з розбором HTML, а виконується, коли DOM уже повний. Не треба переносити теги в кінець <body> і обгортати код у слухач DOMContentLoaded, а порядок кількох скриптів зберігається.

<head>
  <link rel="stylesheet" href="css/main.css">
  <script src="js/app.js" defer></script>
</head>

Квіз для самоперевірки

Запитання перевіряють розуміння механізмів, а не визначення. Після кожної відповіді з'явиться пояснення; прогрес зберігається в цьому браузері.
