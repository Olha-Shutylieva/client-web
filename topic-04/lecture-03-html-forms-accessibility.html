HTML-форми та доступність

Клієнтські технології вебпрограмування. Спеціальність 122 «Комп’ютерні науки».

Після лекції ви зможете

  • пояснити, як браузер збирає дані форми і що змінюють action, method та name;

Теоретичний матеріал

Наскрізний приклад лекції — форма реєстрації читача в онлайн-каталозі книжок: ім’я, email, телефон, формат книжок, коментар і кнопка надсилання. Кожне поняття розбираємо за схемою «проблема → чому так → рішення → коли застосовувати».

Форма, action і method: як дані потрапляють на сервер

Проблема. Поля введення самі по собі — лише окремі елементи на сторінці. Якщо вони не об’єднані формою, браузер не знає, що їх треба надіслати разом, куди саме і яким способом. Тоді все доводиться збирати вручну на JavaScript, а разом із цим зникають безкоштовні речі: надсилання клавішею Enter, вбудована валідація, автозаповнення.

Чому так. Елемент <form> — це контейнер, який описує запит. Під час надсилання браузер обходить усі елементи керування форми і складає набір даних форми: для кожного поля, що має атрибут name і не вимкнене через disabled, додається пара name=value. Поле без name у запит не потрапляє взагалі, навіть якщо в нього є id: id потрібен для зв’язку з label, CSS і JavaScript, а ключем у даних є саме name. Непозначений прапорець теж не надсилається, а позначений без атрибута value надсилає значення on. Поля з readonly, на відміну від disabled, надсилаються.

Рішення. Атрибут action задає адресу, куди йде запит; якщо його немає, форма надсилається на адресу поточної сторінки. Атрибут method задає HTTP-метод: за замовчуванням get — пари стають рядком запиту в URL (/readers?email=anna%40example.com), а з post вони йдуть у тілі запиту і не видні в адресному рядку. Для завантаження файлів потрібні method="post" і enctype="multipart/form-data".

Коли фокус стоїть у текстовому полі форми, натискання Enter запускає неявне надсилання — браузер поводиться так, ніби користувач натиснув першу кнопку надсилання. Це ще одна причина використовувати справжню форму, а не набір полів у div.

Якщо дані треба обробити на клієнті, не відмовляйтеся від форми, а перехопіть подію submit. Вона спрацьовує лише тоді, коли вбудована валідація пройшла, тож у обробник потрапляють уже перевірені дані. Об’єкт FormData збирає той самий набір пар, що й браузер під час звичайного надсилання.

Коли застосовувати. get — для запитів, що лише читають дані: пошук, фільтр каталогу, сортування. Такий URL можна зберегти в закладки чи надіслати колезі. post — для всього, що змінює дані або містить чутливу інформацію: реєстрація, вхід, замовлення. Пароль у рядку запиту осяде в історії браузера та журналах сервера.

Механізм, який варто запам’ятати. Для програмного надсилання використовуйте form.requestSubmit(): він проходить той самий шлях, що й клік по кнопці, — валідацію і подію submit. Старіший form.submit() надсилає форму в обхід валідації і без події submit.

Типи input: чому type — це не лише зовнішній вигляд

Проблема. Якщо всі поля мають type="text", браузер не знає, що в полі очікується email, число чи дата. Він не перевірить формат, не підкаже, як виправити помилку, а на телефоні покаже звичайну літерну клавіатуру замість клавіатури з символом @ чи цифрами.

Чому так. Значення type вмикає для поля одразу кілька механізмів. Перший — алгоритм очищення значення: наприклад, поле number не прийме в value рядок, що не є числом, а date завжди зберігає дату у форматі YYYY-MM-DD, хоч користувач бачить її у форматі своєї локалі. Другий — перевірка відповідності типу: email і url отримують прапорець typeMismatch, якщо значення не схоже на адресу. Третій — інтерфейс: календар для date, стрілки для number, приховування символів для password. Четвертий — підказка віртуальній клавіатурі.

Важлива деталь: властивість value будь-якого поля завжди повертає рядок, навіть для type="number". Для числа існує valueAsNumber (порожнє поле дає NaN), для дат — valueAsDate. Тому input.value + 1 для поля зі значенням 3 дає "31", а не 4.

Рішення. Обирайте type за змістом даних, а не за виглядом. Зверніть увагу на два винятки. type="tel" не перевіряє формат взагалі, бо формати номерів у різних країнах різні; він дає телефонну клавіатуру і семантику для автозаповнення, а формат задають атрибутом pattern. type="number" призначений для кількостей, з якими можна рахувати; для значень, що лише складаються з цифр — поштовий індекс, номер читацького квитка, код з SMS, — краще type="text" з inputmode="numeric": клавіатура цифрова, але без стрілок, прокрутки колесом і перетворення на число.

Коли застосовувати. Завжди, коли для даних існує відповідний тип: email, tel, url, number, date, time, password, search, checkbox, radio, file. Атрибут inputmode — лише підказка клавіатурі, він не вмикає валідацію, тому не замінює правильний type.

Підпис поля: label і зв’язок for/id

Проблема. Текст «Email», що просто стоїть поруч із полем, для браузера — окремий абзац. Користувач, який бачить сторінку, здогадується про зв’язок з розташування. Скрінрідер, переходячи на поле, оголосить лише «поле редагування» — без назви, і людина не знає, що вводити. Людині з тремором доводиться влучати в маленьке поле, бо клік по тексту нічого не робить.

Чому так. Допоміжні технології працюють не з пікселями, а з деревом доступності, яке браузер будує з DOM. Для кожного елемента керування там є роль (поле редагування, прапорець, кнопка), доступне ім’я і стани. Доступне ім’я поля береться з програмно пов’язаного підпису. Елемент <label> створює саме такий зв’язок: його текст стає ім’ям поля, а клік по ньому передає фокус полю, а для прапорця чи перемикача — ще й змінює його стан.

Рішення. Зв’язок задається двома способами. Явний: атрибут for у label дорівнює id поля, і id має бути унікальним на сторінці. Неявний: поле вкладене всередину label. Явний спосіб гнучкіший для верстки, тому його використовують частіше. Додаткову підказку, яка не є назвою поля, пов’язують через aria-describedby: скрінрідер прочитає її після імені.

Якщо підпису немає, браузер шукає запасні джерела імені: aria-labelledby, aria-label, title і, в останню чергу, placeholder. Тобто поле лише з placeholder скрінрідер іноді й назве, але зряча людина втратить підказку щойно почне вводити текст, а світло-сірий колір placeholder часто не має достатнього контрасту.

Коли застосовувати. Для кожного input (крім hidden і кнопок), select і textarea. Видимий label — варіант за замовчуванням; aria-label залишайте для рідкісних випадків, коли призначення поля очевидне з візуального контексту, наприклад поле пошуку поруч із кнопкою «Знайти».

fieldset і legend, select, textarea, button

Проблема. Група перемикачів «Паперова», «Електронна», «Аудіо» зрозуміла лише разом із запитанням «Формат книжки». Кожен перемикач має власний label, але саме запитання ні з чим не пов’язане, тож скрінрідер оголосить «Паперова, перемикач» без контексту.

Чому так і рішення. <fieldset> об’єднує пов’язані поля в групу, а перший дочірній <legend> стає назвою цієї групи. Коли фокус заходить у групу, скрінрідер оголошує легенду, а потім конкретне поле. Бонус: атрибут disabled на fieldset вимикає всі поля всередині (крім тих, що в самій легенді). Для перемикачів required достатньо поставити на будь-який із групи з однаковим name — тоді вимагається вибір одного з них.

<select> надсилає атрибут value вибраного option, а якщо його немає — текст опції. Перша опція з порожнім value разом з required працює як запрошення «Оберіть…»: поки вибрана вона, поле вважається незаповненим. <optgroup> групує опції у списку. У <textarea> немає атрибута value: початковий текст пишуть між тегами, і всі пробіли та переноси всередині зберігаються.

<button> має три типи, і тип за замовчуванням — submit. Тобто кнопка без type усередині форми надсилає форму, навіть якщо ви мали на увазі «Очистити кошик» чи «Показати пароль». Для дій на JavaScript потрібен type="button", а type="reset" повертає поля до початкових значень і на практиці частіше шкодить, ніж допомагає. Порівняно з <input type="submit"> кнопка може містити розмітку, наприклад іконку поруч із текстом.

Коли застосовувати. fieldset — для груп перемикачів і прапорців та для логічних блоків довгої форми («Контакти», «Адреса доставки»). select — коли варіантів багато і вони відомі наперед; якщо варіантів два-п’ять, перемикачі показують усі одразу і вимагають менше дій. Тип кнопки вказуйте завжди, навіть для submit, — так намір видно з коду.

Вбудована валідація: атрибути, ValidityState і повідомлення

Проблема. Користувачі помиляються: пропускають обов’язкові поля, вводять «анна.gmail.com» замість email, кількість 50 там, де максимум 5. Перевіряти це все вручну на JavaScript довго, а якщо не перевіряти — сервер отримає сміття, а людина дізнається про помилку лише після перезавантаження сторінки.

Чому так. Браузер реалізує constraint validation — перевірку обмежень, описаних атрибутами. У кожного поля є об’єкт validity типу ValidityState з логічними прапорцями: valueMissing (порушено required), typeMismatch (формат email/url), patternMismatch, tooShort і tooLong (minlength/maxlength), rangeUnderflow і rangeOverflow (min/max), stepMismatch, badInput (браузер не зміг перетворити введене, наприклад літери в полі number) і customError. Узагальнювальний прапорець valid дорівнює true, лише якщо всі інші — false. Під час надсилання браузер перевіряє всі поля, для кожного невалідного генерує подію invalid, переводить фокус на перше з них, показує повідомлення і скасовує надсилання — подія submit навіть не настає.

Кілька деталей механізму, на яких часто помиляються. pattern завжди перевіряє все значення: браузер неявно обгортає вираз у ^(?:…)$, тому [0-9]{5} не пропустить шість цифр. Сучасні браузери компілюють pattern з прапорцем v, тож деякі символи в квадратних дужках, зокрема дефіс поза діапазоном, треба екранувати; некоректний вираз браузер просто ігнорує. Усі обмеження, крім required, не перевіряють порожнє значення — порожнє необов’язкове поле з pattern валідне. minlength і maxlength перевіряються лише для значень, які ввів користувач, а не для встановлених скриптом; maxlength до того ж просто не дає ввести зайві символи.

Рішення для стилів. Псевдоклас :invalid спрацьовує одразу після завантаження, тож порожні обов’язкові поля червоніють ще до того, як людина щось ввела. Псевдоклас :user-invalid (Baseline з 2023 року) спрацьовує лише після взаємодії з полем або спроби надсилання — саме він потрібен для підсвічування помилок.

Рішення для повідомлень. Стандартні повідомлення браузера — мовою браузера і загальні («Заповніть це поле»). Щоб пояснити, що саме виправити, використовують API: setCustomValidity(message) робить поле невалідним з вашим текстом (customError), а порожній рядок знімає цю помилку. checkValidity() повертає true/false, reportValidity() ще й показує повідомлення, validationMessage містить поточний текст помилки.

Коли застосовувати. Атрибути валідації — завжди, коли обмеження відоме: вони працюють без JavaScript і дають браузеру знати, яке поле невалідне. Атрибут novalidate на формі вимикає лише перевірку під час надсилання (прапорці validity і псевдокласи працюють далі) — його ставлять, коли ви показуєте помилки власним інтерфейсом. І головне: валідація на клієнті — це зручність, а не захист. Запит можна надіслати в обхід сторінки, тому сервер перевіряє дані повторно.

autocomplete: підказка браузеру, що це за дані

Проблема. Користувач уже десятки разів вводив своє ім’я, email і адресу, але на кожному новому сайті робить це знову. Людям з руховими чи когнітивними порушеннями це особливо важко, а менеджер паролів не розуміє, куди підставити збережений пароль, а куди запропонувати новий.

Чому так. Браузер не може надійно вгадати зміст поля з його name чи підпису: name="n1" нічого не каже. Атрибут autocomplete приймає стандартизовані токени, які прямо описують призначення поля: name, given-name, family-name, email, tel, street-address, postal-code, bday, username, current-password, new-password, one-time-code та інші. Токени можна уточнювати префіксами, наприклад shipping postal-code і billing postal-code, щоб розрізнити дві адреси в одній формі.

Рішення і коли застосовувати. Ставте токен кожному полю, яке збирає дані про самого користувача. Це також вимога WCAG 2.2 (критерій 1.3.5 «Визначення мети введення», рівень AA). current-password — для входу, new-password — для реєстрації та зміни пароля: тоді менеджер паролів запропонує згенерувати надійний. autocomplete="off" доречний для даних, які не повторюються (одноразовий код бронювання, капча), але для полів входу багато браузерів його свідомо ігнорують.

Основи ARIA і перше правило ARIA

Проблема. Не все в інтерфейсі можна описати нативним HTML: повідомлення про помилку, що з’являється динамічно, зв’язок поля з текстом помилки, стан «невалідне». Водночас ARIA часто використовують як «латку» для елементів, які просто обрано неправильно.

Чому так. WAI-ARIA — набір атрибутів, що змінюють лише те, як елемент подано в дереві доступності: ролі (role="alert"), властивості (aria-describedby, aria-label) і стани (aria-invalid, aria-expanded). ARIA не додає поведінки. <div role="button"> скрінрідер назве кнопкою, але він не отримає фокус через Tab, не спрацює від Enter чи Space і не надішле форму — усе це доведеться дописувати вручну.

Рішення. Перше правило використання ARIA від W3C: якщо існує нативний HTML-елемент або атрибут з потрібною семантикою і поведінкою, використовуйте його, а не перепрофільовуйте інший елемент за допомогою ARIA. Посібник WAI-ARIA Authoring Practices формулює це ще коротше: відсутність ARIA краща за неправильну ARIA. Для форм ARIA потрібна у вузьких випадках: зв’язати поле з підказкою і текстом помилки (aria-describedby), позначити поле як невалідне тоді, коли ви показуєте помилку (aria-invalid="true"), оголосити динамічне повідомлення (role="alert" або aria-live). aria-required поруч із нативним required зайвий — браузер уже передає цей стан.

Коли застосовувати. Лише тоді, коли нативного рішення немає. Контейнер з role="alert" має бути в DOM заздалегідь, а текст у нього вставляють пізніше: скрінрідер оголошує саме зміну вмісту, а елемент, що з’явився разом із текстом, може бути пропущений.

Навігація з клавіатури і видимий фокус

Проблема. Частина людей не користується мишею: через рухові порушення, зі скрінрідером або просто тому, що заповнювати форму з клавіатури швидше. Якщо елемент не отримує фокус, його не натиснути; якщо фокус не видно, незрозуміло, де ви зараз.

Чому так. Клавіша Tab переводить фокус на наступний елемент у послідовному порядку фокусу, Shift+Tab — на попередній. Порядок визначається порядком елементів у DOM, а не їхнім положенням на екрані. Нативні a[href], button, input, select, textarea фокусуються самі і мають стандартну клавіатурну поведінку: Space перемикає прапорець, Enter і Space натискають кнопку, у групі перемикачів Tab заходить один раз, а стрілки переміщують вибір між варіантами.

Рішення. Використовуйте нативні елементи — і клавіатурна підтримка буде з коробки. tabindex="0" додає в порядок фокусу нестандартний елемент (якщо без цього не обійтися), tabindex="-1" дозволяє фокусувати елемент лише скриптом, наприклад перевести фокус на підсумок помилок. Додатні значення tabindex ламають природний порядок і є антипатерном. Стандартну обвідку фокусу можна змінити, але не прибрати: псевдоклас :focus-visible спрацьовує тоді, коли браузер вважає, що фокус треба показати (клавіатура, текстові поля), і не заважає клікам мишею по кнопках.

Коли застосовувати. Перевіряйте кожну форму без миші: пройдіть її Tab від початку до кінця, заповніть, надішліть Enter. Це відповідає критеріям WCAG 2.2 2.1.1 «Клавіатура» і 2.4.7 «Видимий фокус»; індикатор фокусу також має бути контрастним щонайменше 3:1 до фону (1.4.11).

Інтерактивне демо

Дві лабораторії. У першій ви збираєте поле з атрибутів і бачите, як реагує вбудована валідація. У другій — порівнюєте, що скрінрідер отримує від поля з підписом і без нього.

Конструктор поля форми

Оберіть type, змініть атрибути, а потім вводьте різні значення в поле праворуч. Спробуйте надіслати форму з помилкою: браузер покаже власну підказку і не дасть події submit статися. Атрибути, які для обраного типу не діють, згруповані у вимкнений fieldset — це той самий механізм, що й у реальних формах.

    Шпаргалка: форми та доступність

    Каркас форми

    • <form action="/url" method="post"> — куди і як надіслати
    • method: get (URL, за замовч.) / post (тіло запиту)
    • enctype="multipart/form-data" — для файлів
    • У запит іде лише поле з name, не disabled
    • new FormData(form), data.get(), data.getAll()
    • form.requestSubmit() — з валідацією; submit() — без

    Типи input

    • email, url — перевірка формату (typeMismatch)
    • tel — клавіатура телефону, формат лише через pattern
    • number — кількості; valueAsNumber
    • date — значення завжди YYYY-MM-DD
    • password, search, checkbox, radio, file
    • inputmode="numeric" — цифрова клавіатура без валідації
    • input.value — завжди рядок

    Підпис і опис поля

    • <label for="x"> + <input id="x"> — явний зв’язок
    • <label><input> Текст</label> — неявний
    • Клік по label = фокус / перемикання поля
    • aria-describedby="hint-id error-id" — підказка й помилка
    • placeholder — приклад значення, не назва

    Групування, вибір, текст

    • <fieldset><legend> — назва групи полів
    • fieldset disabled — вимикає всі поля групи
    • Радіо: один name на групу; required на одному
    • <option value="">Оберіть… + required
    • <optgroup label> — групи опцій
    • <textarea>текст</textarea> — без атрибута value

    Кнопки

    • type="submit" — за замовчуванням у формі
    • type="button" — для дій на JavaScript
    • type="reset" — скидає поля (рідко потрібна)
    • formnovalidate — ця кнопка надсилає без перевірки
    • Enter у текстовому полі — неявне надсилання

    Атрибути валідації

    • required → valueMissing
    • pattern → patternMismatch (усе значення, прапорець v)
    • minlength/maxlength → tooShort/tooLong
    • min/max → rangeUnderflow/rangeOverflow
    • step → stepMismatch
    • Порожнє значення перевіряє лише required
    • novalidate на form — власний інтерфейс помилок

    Constraint Validation API

    • el.validity.valid та інші прапорці
    • el.checkValidity() — true/false + подія invalid
    • el.reportValidity() — ще й показує повідомлення
    • el.setCustomValidity('текст'); '' — зняти
    • el.validationMessage — поточний текст помилки
    • CSS: :user-invalid замість :invalid

    autocomplete

    • name, given-name, family-name
    • email, tel, url, bday
    • street-address, postal-code, country-name
    • username, current-password, new-password
    • one-time-code — код з SMS
    • shipping / billing — префікси секцій

    Клавіатура і фокус

    • Tab / Shift+Tab — порядок DOM
    • Space — прапорець, кнопка; Enter — кнопка, посилання
    • Стрілки — вибір у групі перемикачів і в select
    • tabindex="0" — у порядок; "-1" — лише скриптом
    • tabindex > 0 — ніколи
    • :focus-visible { outline: … } — змінюйте, не прибирайте

    ARIA мінімум

    • Правило №1: нативний елемент замість ARIA
    • ARIA змінює опис у дереві доступності, не поведінку
    • aria-invalid="true" — коли показуєте помилку
    • role="alert" / aria-live="polite" — динамічні повідомлення
    • aria-label — ім’я без видимого тексту (рідко)
    • aria-required поруч із required — зайве

    Антипатерни

    Кожен з цих фрагментів «працює» на екрані розробника з мишею. Проблеми з’являються в іншого користувача — на телефоні, з клавіатурою, зі скрінрідером.

    Placeholder замість label

    Чому це погано. Placeholder зникає з першим введеним символом, тож людина, яку відволікли, вже не бачить, що це за поле, а перевірити заповнену форму перед надсиланням неможливо. Його світло-сірий текст зазвичай не проходить вимогу контрасту 4.5:1. Для скрінрідера placeholder — лише останнє запасне джерело імені, на яке не всі комбінації браузера й допоміжних технологій покладаються однаково.

    div з onclick замість button

    Чому це погано. div не потрапляє в порядок фокусу, тому з клавіатури до нього не дістатися. Він не реагує на Enter і Space, а скрінрідер оголосить його як звичайний текст, без ролі кнопки. Щоб це виправити, довелося б додати role="button", tabindex="0" і обробку клавіш — тобто вручну відтворити те, що button має з коробки.

    type="text" для email і телефону

    Чому це погано. Браузер не знає, що в полі очікується адреса, тому не перевіряє формат і не допомагає виправити помилку — «anna.gmail.com» потрапить на сервер. На телефоні відкриється літерна клавіатура без @ чи цифр, а автозаповнення не зрозуміє, які дані підставити.

    Прибраний outline без заміни

    Чому це погано. Фокус нікуди не зникає — елементи й далі його отримують, — але стає невидимим. Користувач клавіатури натискає Tab і не знає, яке поле зараз активне і що зробить Enter. Це пряме порушення критерію WCAG 2.4.7 «Видимий фокус».

    ARIA там, де вистачає нативного елемента

    Чому це погано. ARIA змінює лише опис у дереві доступності. Щоб такий «прапорець» працював, треба вручну обробляти Space, перемикати aria-checked і окремо відправляти значення на сервер — форма його не надішле, бо це не поле. Кожен такий ручний механізм — місце для помилки, і коли опис розходиться з поведінкою, скрінрідер обманює користувача. role="button" на button просто дублює нативну роль, а aria-required на кнопці не має сенсу.

    button без type усередині форми

    Чому це погано. Тип кнопки за замовчуванням — submit. Після кліку спочатку виконується обробник, а потім браузер надсилає форму: сторінка перезавантажується, введені дані губляться або, гірше, недозаповнена форма потрапляє на сервер.

    Додатний tabindex для «правильного» порядку

    Чому це погано. Елементи з додатним tabindex отримують фокус раніше за всі інші на сторінці, незалежно від місця в DOM. Порядок фокусу розходиться з візуальним і з порядком читання скрінрідера, а кожне нове поле змушує перенумеровувати всю сторінку.

    Помилка, позначена лише кольором

    Чому це погано. Людина з порушенням колірного зору може не відрізнити червону рамку від звичайної, а скрінрідер про колір не повідомляє взагалі. Навіть побачивши рамку, користувач не знає, що саме не так і як це виправити. Порушуються критерії WCAG 1.4.1 «Використання кольору» і 3.3.1 «Ідентифікація помилки».

    Бест практики

    Кожне поле — з видимим label

    Видимий підпис допомагає всім одночасно: зрячій людині він нагадує, що вводити, скрінрідеру дає доступне ім’я, а людині з тремором — більшу область для кліку. Розміщуйте підпис перед полем (для прапорців і перемикачів — після) і формулюйте його так, як користувач називає ці дані.

    Групуйте пов’язані поля в fieldset з legend

    Легенда дає групі назву, яку скрінрідер оголошує при вході в неї, тож відповіді «Так»/«Ні» чи «Паперова»/«Аудіо» не втрачають запитання. Для довгих форм групування ще й ділить форму на смислові частини, які легше перевірити.

    Правильний type для кожних даних

    Тип вмикає перевірку формату, потрібну клавіатуру на телефоні й зручний інтерфейс вибору без жодного рядка JavaScript. Коли дані лише складаються з цифр, але не є числом, поєднуйте type="text" з inputmode.

    autocomplete з точним токеном

    Браузер і менеджер паролів заповнять поле за секунду, а людині не доведеться пам’ятати і вводити дані знову. Токен описує призначення поля незалежно від його name, тож працює і з вашими внутрішніми назвами.

    Зрозумілі повідомлення про помилки

    Добре повідомлення каже, що не так і як це виправити, стоїть поруч із полем і пов’язане з ним через aria-describedby, тож скрінрідер прочитає його разом з назвою поля. Показуйте помилку після взаємодії — :user-invalid замість :invalid, — щоб порожня форма не зустрічала людину червоним.

    Обов’язковість позначайте текстом

    Зірочка чи червоний колір без пояснення — умовність, яку не всі знають і не всі бачать. Слово «обов’язкове» в підписі (або «необов’язкове», якщо таких полів менше) зрозуміле кожному, а атрибут required передає цей стан скрінрідеру.

    Дублюйте перевірку на сервері

    Валідацію в браузері легко обійти: вимкнути в інструментах розробника або надіслати запит напряму. Клієнтська перевірка потрібна для зручності й швидкого зворотного зв’язку, а цілісність даних гарантує лише сервер. Тому правила краще описувати так, щоб їх можна було застосувати в обох місцях.

    Квіз для самоперевірки

    12 запитань на розуміння механізмів. Оберіть варіант і натисніть «Відповісти» — одразу побачите пояснення. Прогрес зберігається в цьому браузері.
