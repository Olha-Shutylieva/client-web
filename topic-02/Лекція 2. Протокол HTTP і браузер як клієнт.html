Протокол HTTP і браузер як клієнт

Що саме браузер пише серверу і що читає у відповідь, як кеш заощаджує мережу, як побачити все це в DevTools — і хто домовляється про правила, за якими працюють усі браузери.

Після лекції ви зможете

  • прочитати й скласти HTTP-повідомлення: рядок запиту чи статусу, заголовки, порожній рядок, тіло;
  • обрати метод і код стану за їхньою семантикою, розуміючи безпечність та ідемпотентність;
  • пояснити, які заголовки браузер додає сам і які обмеження накладає на запити зі сторінки;
  • налаштувати кешування через Cache-Control, валідатори й версіоновані імена файлів і перевірити його в DevTools;
  • аналізувати мережу в панелі Network: фільтри, колонки, Initiator, Timing, throttling, HAR;
  • пояснити, як народжуються вебстандарти в IETF, W3C, WHATWG і TC39 та шлях нової можливості в ECMAScript.

Теорія

Продовжуємо з каталогом книжок, але тепер він має API: /api/books повертає список книжок у JSON, /api/books/2 — одну книжку. На ньому розберемо кожну частину розмови браузера з сервером.

Структура HTTP-повідомлень

Браузер написаний на C++, сервер — на JavaScript, Java чи Go, і створювали їх люди, які ніколи не бачили коду одне одного. Щоб такі програми розуміли одна одну, формат повідомлення має бути однозначним для машини, розширюваним без зміни самого протоколу і, бажано, читабельним для людини, яка налагоджує проблему.

HTTP/1.1 вирішує це текстовим форматом із чотирьох частин. Перша — стартовий рядок. У запиті це метод, ціль запиту (шлях із рядком запиту) та версія протоколу, у відповіді — версія, тризначний код стану й текстова фраза. Друга частина — поля заголовків, по одному на рядок у форматі Name: value; регістр імені не важливий, тож content-type і Content-Type — те саме поле. Третя — порожній рядок, єдиний сигнал, що заголовки скінчилися. Четверта — необов'язкове тіло. Його довжину отримувач дізнається із заголовка Content-Length або з передачі частинами (Transfer-Encoding: chunked), коли розмір заздалегідь невідомий.

POST /api/books HTTP/1.1
Host: books.example.com
Content-Type: application/json
Content-Length: 71
Accept: application/json

{"title":"Learning Web Design","author":"Jennifer Robbins","year":2018}
HTTP/1.1 201 Created
Location: /api/books/4
Content-Type: application/json
Content-Length: 78

{"id":4,"title":"Learning Web Design","author":"Jennifer Robbins","year":2018}

З 2022 року HTTP описано набором документів IETF, у якому семантика відокремлена від транспорту. RFC 9110 визначає методи, коди стану й заголовки, спільні для всіх версій, а RFC 9112, 9113 і 9114 описують, як ці повідомлення передаються в HTTP/1.1, HTTP/2 і HTTP/3. HTTP/2 і HTTP/3 — бінарні протоколи: стартовий рядок перетворюється на псевдозаголовки :method, :path, :scheme, :authority у запиті та :status у відповіді, імена заголовків записуються малими літерами й стискаються, а текстової фрази на кшталт «OK» немає зовсім. Зміст розмови при цьому той самий, тому все, що ви вивчите на прикладах HTTP/1.1, працює й у новіших версіях.

Коли це знадобиться. У DevTools перемикач Raw у вкладці Headers показує заголовки майже в такому вигляді. Розуміння структури потрібне, коли ви налагоджуєте запит, формуєте тіло для fetch чи пояснюєте, чому сервер «не бачить» тіло без правильного Content-Type.

Методи

Та сама адреса /api/books/2 може означати «покажи книжку», «заміни її», «зміни рік видання» чи «видали». Самої адреси замало, причому не лише серверу. Кешу треба знати, чи можна зберегти відповідь. Браузеру — чи можна повторити запит після обриву з'єднання і чи треба попередити користувача, що він відправить форму вдруге. Пошуковому роботу — чи безпечно переходити за посиланням.

Тому кожен запит містить метод, який описує намір. GET отримує поточне представлення ресурсу. HEAD робить те саме, але без тіла: так перевіряють наявність ресурсу, розмір чи дату зміни. POST передає дані на обробку за правилами самого ресурсу — створити запис, надіслати форму, запустити дію. PUT повністю замінює стан ресурсу за вказаною адресою або створює його. PATCH (RFC 5789) змінює лише частину ресурсу. DELETE видаляє. OPTIONS питає, що дозволено з ресурсом, і браузер використовує його для попередньої перевірки CORS.

GET     /api/books      read the list of books
GET     /api/books/2    read one book
HEAD    /api/books/2    same headers as GET, no body
POST    /api/books      create a book, the server chooses the id
PUT     /api/books/2    replace book 2 with the full new version
PATCH   /api/books/2    change some fields of book 2
DELETE  /api/books/2    delete book 2
OPTIONS /api/books      ask which methods are allowed

Важливіші за назви методів — три їхні властивості. Безпечний метод за задумом нічого не змінює на сервері; такі методи — GET, HEAD, OPTIONS і TRACE. Саме тому браузер може попередньо завантажувати сторінки за посиланнями, а роботи — обходити сайт. Ідемпотентний метод при повторенні призводить до того самого стану сервера, що й одноразовий виклик. Це всі безпечні методи, а також PUT і DELETE. Тож другий DELETE /api/books/2 не видалить «ще щось», хоча його відповідь буде вже 404: ідемпотентність стосується стану, а не відповіді. Ідемпотентні запити клієнт може автоматично повторити після обриву з'єднання. POST і PATCH ідемпотентності не гарантують, тому браузер перед повторною відправкою форми питає користувача. Кешованими на практиці є відповіді на GET і HEAD.

HTML-форми вміють лише два методи: method="get" додає поля до адреси як рядок запиту, а method="post" кладе їх у тіло. Решту методів сторінка надсилає через JavaScript.

Коли це знадобиться. Щоразу, коли ви проєктуєте адреси й дії в застосунку або читаєте документацію API. Неправильно обраний метод не дає помилки одразу, але ламає кешування, повторні запити й безпеку, і проявляється це пізніше та непередбачувано.

Коди стану

Отримавши відповідь, клієнт має автоматично вирішити, що робити: показати сторінку, перейти за новою адресою, взяти копію з кешу, попросити користувача увійти чи показати помилку. Текст «Сторінку не знайдено» програма зрозуміти не може, потрібен короткий машинозчитуваний результат. Ним і є тризначний код стану. Перша цифра задає клас, і клієнт, отримавши незнайомий код, поводиться з ним як із загальним кодом класу: невідомий 418 він трактує як 400.

1xx — інформаційні. Їх майже не видно в повсякденній роботі. 101 Switching Protocols з'являється при переході на WebSocket, а 103 Early Hints дає змогу серверу підказати браузеру, які ресурси підвантажувати, ще до готовності основної відповіді.

2xx — успіх. 200 OK — звичайна успішна відповідь з тілом. 201 Created означає, що створено новий ресурс, а його адреса — в заголовку Location. 204 No Content — успіх без тіла, типовий для DELETE. 206 Partial Content віддає частину файлу на запит із заголовком Range; так перемотують відео.

3xx — перенаправлення. 301 Moved Permanently і 308 Permanent Redirect повідомляють про постійний переїзд ресурсу, 302 Found і 307 Temporary Redirect — про тимчасовий. Різниця всередині пар історична: після 301 і 302 браузери перетворюють POST на GET, а 307 і 308 гарантують збереження методу й тіла. 303 See Other явно наказує зробити GET на іншу адресу; це основа шаблону Post/Redirect/Get, завдяки якому оновлення сторінки після відправки форми не надсилає її вдруге. 304 Not Modified — не перенаправлення, а відповідь на умовний запит: «твоя копія актуальна».

4xx — помилка клієнта, тобто проблема в запиті, і повторювати його без змін марно. 400 Bad Request — запит некоректний, наприклад зламаний JSON. 401 Unauthorized, попри назву, означає «не автентифіковано»: сервер не знає, хто ви, і в заголовку WWW-Authenticate пояснює, як представитися. 403 Forbidden — сервер знає, хто ви, але дії не дозволяє. 404 Not Found — ресурсу немає. 405 Method Not Allowed супроводжується заголовком Allow зі списком дозволених методів. 406 Not Acceptable — сервер не може віддати жоден із форматів з Accept. 409 Conflict — конфлікт із поточним станом ресурсу. 413 Content Too Large — тіло завелике. 415 Unsupported Media Type — сервер не приймає такий Content-Type. 422 Unprocessable Content — формат правильний, але дані не проходять перевірку. 429 Too Many Requests — перевищено ліміт запитів; заголовок Retry-After підказує, коли пробувати знову.

5xx — помилка сервера: запит, можливо, коректний, але сервер його не виконав. 500 Internal Server Error — загальна помилка. 502 Bad Gateway і 504 Gateway Timeout повертає проміжний сервер, коли сервер за ним відповів некоректно або не відповів вчасно. 503 Service Unavailable — тимчасове перевантаження чи обслуговування.

Важлива деталь для JavaScript: fetch завершується помилкою лише тоді, коли відповіді немає взагалі — мережа недоступна чи запит заблоковано. Відповідь 404 чи 500 з погляду fetch успішна, бо сервер відповів. Перевіряти результат має ваш код, через властивості response.ok (true для 200–299) і response.status. Детально fetch розглянемо в лекціях про роботу з API.

async function loadBook(id) {
  const response = await fetch(`/api/books/${id}`);
  if (!response.ok) {
    throw new Error(`Book ${id} was not loaded: HTTP ${response.status}`);
  }
  return response.json();
}

function describeStatus(status) {
  if (status >= 500) return "server error";
  if (status >= 400) return "client error";
  if (status >= 300) return "redirect or not modified";
  if (status >= 200) return "success";
  return "informational";
}

console.log(describeStatus(404)); // "client error"

Коли це знадобиться. Код стану — перше, на що дивитися в колонці Status панелі Network. За ним одразу видно, з якого боку шукати проблему: 4xx — у запиті чи правах клієнта, 5xx — на сервері.

Заголовки

Метод, шлях і код стану не кажуть, у якому форматі дані, якою мовою, чи стиснуті вони, скільки їх можна кешувати, хто їх запитує і чи має на це право. Розширювати стартовий рядок під кожну таку потребу неможливо. Тому HTTP має відкритий механізм заголовків: нове поле можна додати, не змінюючи протоколу, а клієнти, які його не знають, просто ігнорують. Корисно групувати заголовки за призначенням.

Про представлення — що саме лежить у тілі. Content-Type задає медіатип і кодування: text/html; charset=utf-8, text/css, text/javascript (саме цей тип RFC 9239 закріпив для JavaScript), application/json, image/avif, font/woff2. Content-Length — розмір тіла в байтах. Content-Encoding — яким алгоритмом тіло стиснуто: gzip, br (Brotli) чи zstd.

Узгодження вмісту. Клієнт описує, що вміє прийняти: Accept (формати), Accept-Language (мови), Accept-Encoding (стиснення). Сервер обирає найкращий варіант і заголовком Vary повідомляє кешам, від яких заголовків запиту залежала відповідь, щоб українська версія не віддалася англомовному користувачу з кешу.

Контекст і автентифікація. Host — ім'я сайту. User-Agent — опис клієнта. Referer (саме так, з історичною помилкою в написанні) — адреса сторінки, з якої йде запит. Origin — походження сторінки для міжсайтових запитів. Authorization передає облікові дані, наприклад Bearer-токен.

Стан. HTTP не пам'ятає попередніх запитів, тому сервер видає Set-Cookie, а браузер повертає значення в Cookie з кожним наступним запитом до цього сайту. Атрибути керують безпекою: HttpOnly ховає cookie від JavaScript, Secure дозволяє лише HTTPS, SameSite обмежує надсилання з інших сайтів.

Кешування, перенаправлення, безпека. Cache-Control, ETag, Last-Modified, If-None-Match, Age розберемо в розділі про кеш. Location вказує нову адресу, Allow — дозволені методи, Retry-After — коли повторити. Strict-Transport-Security, Content-Security-Policy і X-Content-Type-Options: nosniff вмикають захисні механізми браузера. Власні заголовки застосунку колись позначали префіксом X-, але RFC 6648 цю домовленість скасував: нове поле просто отримує зрозуміле ім'я.

GET /api/books HTTP/1.1
Host: books.example.com
Accept: application/json
Accept-Language: uk,en;q=0.8
Accept-Encoding: gzip, deflate, br, zstd
Authorization: Bearer eyJhbGciOi...
Cookie: theme=dark

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Encoding: br
Content-Language: uk
Vary: Accept-Language, Accept-Encoding
Cache-Control: private, no-cache
ETag: "v8"
X-Content-Type-Options: nosniff

Параметр q в Accept-Language — це вага переваги від 0 до 1: запис uk,en;q=0.8 означає «найкраще українська, англійська теж підійде».

Коли це знадобиться. Коли файл приходить, але браузер його не застосовує (неправильний Content-Type разом із nosniff), коли сервер не розуміє тіло запиту, коли cookie «не зберігається», коли потрібно перевірити, чи стиснуто ресурс.

Браузер як HTTP-клієнт

Розробник пише лише <img src="cover.avif"> чи fetch("/api/books"), а запит виходить з десятком заголовків, через вже відкрите з'єднання, з cookie і правильним форматом. Хто це вирішує? Браузер — дуже «самостійний» клієнт. Він діє від імені користувача, тож має не лише виконувати бажання сторінки, а й захищати користувача від неї, бо сторінка може бути зловмисною.

Браузер робить три види запитів. Навігація — введена адреса, перехід за посиланням, відправлення форми; її результат замінює поточний документ. Підресурси — стилі, скрипти, шрифти, зображення, які знаходить парсер. Програмні запити — fetch із JavaScript, результат яких отримує код, а не вікно. Для кожного виду браузер сам підставляє доречний Accept: для навігації першим іде text/html, для <img> — формати зображень, які він уміє декодувати.

Також браузер автоматично додає кілька груп заголовків. Це Host і User-Agent; Accept-Encoding зі списком підтримуваних стиснень, причому розпаковує відповідь він теж сам, і ваш код отримує вже розпаковані дані; Accept-Language з налаштувань мови. Далі Cookie для відповідного сайту з урахуванням SameSite і Referer за політикою Referrer-Policy (типово strict-origin-when-cross-origin: на інші сайти йде лише походження, без шляху). Окремо йдуть заголовки метаданих Sec-Fetch-Site, Sec-Fetch-Mode і Sec-Fetch-Dest, з яких сервер дізнається контекст запиту, а також умовні заголовки на основі кешу. Крім того, браузер керує з'єднаннями й пріоритетами: CSS, що блокує рендеринг, завантажується раніше за зображення в кінці сторінки.

Водночас браузер обмежує сторінку. Частину заголовків JavaScript встановити не може взагалі: Host, Cookie, Content-Length, Origin, Referer, Connection, усі Sec-* тощо. Специфікація Fetch називає їх забороненими (forbidden request headers), і спроба їх задати мовчки ігнорується. Інакше скрипт на чужому сайті міг би підробити, від чийого імені й звідки йде запит.

Головне обмеження — політика того самого походження (same-origin policy). Сторінка може надіслати запит на інше походження, але прочитати відповідь її код зможе лише тоді, коли сервер явно дозволить це заголовком Access-Control-Allow-Origin. Цей механізм називається CORS. Для «непростих» запитів — з методами на кшталт PUT чи DELETE або з Content-Type: application/json — браузер спершу надсилає попередній запит OPTIONS (preflight) і відправляє основний лише після дозволу. Зверніть увагу: CORS виконує браузер, а не сервер. Утиліта на кшталт curl отримає ту саму відповідь без жодних обмежень, бо вона не захищає користувача від сторінок.

OPTIONS /api/books/2 HTTP/1.1
Host: api.example.com
Origin: https://books.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://books.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type
Access-Control-Max-Age: 600

Форми показують, як браузер сам будує запит з розмітки.

<!-- GET: fields go to the query string → GET /search?q=css -->
<form action="/search" method="get">
  <label>Title <input name="q"></label>
  <button>Search</button>
</form>

<!-- POST: fields go to the body, Content-Type: application/x-www-form-urlencoded
     → email=reader%40example.com -->
<form action="/subscriptions" method="post">
  <label>Email <input type="email" name="email"></label>
  <button>Subscribe</button>
</form>

Коли це знадобиться. Коли в консолі з'являється помилка CORS, коли заголовок, заданий у fetch, «не доходить» до сервера, коли сервер бачить у запиті заголовки, яких ви не писали. І щоразу, коли треба пояснити, чому той самий запит працює в терміналі, але не зі сторінки.

Кешування

Сторінка каталогу — це документ, кілька стилів і скриптів, шрифти й десятки обкладинок. Якщо щоразу завантажувати все заново, марно витрачаються час користувача, мобільний трафік і ресурси сервера. Але й кешувати навмання не можна. Якщо браузер вперто показує торішній CSS після оновлення сайту, користувач бачить зламану сторінку, а розробник — «у мене все працює».

Кешування HTTP тримається на двох запитаннях. Перше — свіжість: чи можна використати збережену копію, нічого не питаючи в сервера? Друге — валідація: копія вже не свіжа, але, може, вона досі збігається з оригіналом? Відповіді задає сервер заголовками, а виконують кеші. Буває приватний кеш, тобто кеш браузера одного користувача, і спільний — проксі чи CDN, що обслуговує багатьох.

Головний заголовок — Cache-Control з набором директив. max-age=600 означає, що відповідь свіжа 600 секунд від моменту створення; спільні кеші додають заголовок Age, щоб браузер знав, скільки часу копія вже пролежала в них. no-cache часто розуміють неправильно: він не забороняє кешувати, а дозволяє зберегти копію з умовою перевіряти її на сервері перед кожним використанням. Заборону зберігати взагалі задає no-store, і саме вона потрібна для чутливих даних. private дозволяє зберігати лише браузеру, public — і спільним кешам, а s-maxage задає окремий термін для спільних кешів. must-revalidate забороняє використовувати прострочену копію без перевірки. immutable обіцяє, що за час свіжості вміст не зміниться, тож браузер не перевіряє його навіть під час перезавантаження. stale-while-revalidate=60 дозволяє ще хвилину віддавати прострочену копію, поки у фоні оновлюється нова.

Для валідації сервер видає валідатор. ETag — непрозорий ідентифікатор версії, наприклад хеш вмісту. Наступного разу браузер надсилає його в If-None-Match, і, якщо версія та сама, сервер відповідає 304 Not Modified без тіла: кілька сотень байтів замість усього файлу. Старіший валідатор — дата Last-Modified з умовним заголовком If-Modified-Since. Якщо сервер не вказав ні Cache-Control, ні Expires, але надіслав Last-Modified, браузер застосовує евристичне кешування і сам вирішує, скільки вважати копію свіжою; найчастіше це близько 10% часу, що минув від останньої зміни файлу. Тому явний Cache-Control потрібен завжди: без нього поведінкою кешу керує здогадка браузера.

На практиці стратегію будують за типом ресурсу. HTML-документ отримує no-cache з ETag: він завжди актуальний, а 304 робить перевірку дешевою. Статичні файли збирають з хешем вмісту в імені (main.3f9a2c.css) і віддають з max-age=31536000, immutable. Коли вміст змінюється, змінюється й ім'я, HTML посилається на новий файл, і користувачі отримують оновлення одразу, а старий файл у кеші більше просто ніхто не запитує. Персональні відповіді API отримують private і no-cache або короткий max-age, а дані, які взагалі не повинні опинитися на диску, — no-store.

# index.html — always revalidate, cheap 304 if unchanged
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: no-cache
ETag: "page-41"

# css/main.3f9a2c.css — content hash in the name, cache for a year
HTTP/1.1 200 OK
Content-Type: text/css
Cache-Control: max-age=31536000, immutable

# /api/profile — personal data, never store
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

Користувач теж впливає на кеш. Звичайне перезавантаження змушує браузер перевірити документ на сервері, а жорстке (Ctrl+Shift+R, на macOS Cmd+Shift+R) завантажує ресурси заново, оминаючи кеш. Під час розробки зручніше ввімкнути Disable cache у DevTools. Крім HTTP-кешу, у браузера є кеш у пам'яті для ресурсів поточної сесії, кеш «назад/вперед» для миттєвого повернення на попередню сторінку і програмований кеш Service Worker, але всі вони спираються на ті самі принципи.

Коли це знадобиться. Коли після оновлення сайту користувачі бачать стару версію, коли повторне відвідування повільне, хоча нічого не змінилося, і коли треба впевнитися, що особисті дані не потраплять у спільний кеш. Як поводяться різні директиви, можна перевірити в симуляторі кешу.

Аналіз мережі в DevTools

«Сайт гальмує», «дані не з'являються», «стилі старі» — це симптоми, а не діагнози. Гадати можна безкінечно, але браузер записує кожен запит з усіма деталями. Панель Network у DevTools перетворює здогадки на факти, якщо знати, куди дивитися. Запис іде, лише поки DevTools відкриті, тому типовий початок — відкрити панель і перезавантажити сторінку.

Панель інструментів. Кнопка запису і кнопка очищення списку. Preserve log зберігає список запитів між переходами, без нього запит, що зробив перенаправлення, зникає разом зі сторінкою. Disable cache вимикає HTTP-кеш, поки DevTools відкриті. Список Throttling імітує повільну мережу (Fast 4G, Slow 4G, 3G) або її відсутність (Offline); налаштування застосовуються лише до цієї вкладки. Також тут кнопки імпорту й експорту HAR.

Фільтри. Кнопки типів (Fetch/XHR, Doc, CSS, JS, Font, Img, Media, WS та інші) звужують список за видом ресурсу. Поле фільтра приймає не лише фрагмент адреси, а й властивості: status-code:404, method:POST, larger-than:100k, domain:books.example.com, mime-type:image/avif, is:from-cache, has-response-header:cache-control. Мінус перед властивістю інвертує умову: -method:OPTIONS ховає попередні запити CORS. Кілька умов через пробіл поєднуються.

Колонки. Name і Status — що й з яким результатом. Type — тип ресурсу. Initiator — хто запит спричинив: парсер HTML (з номером рядка), CSS-файл (шрифти й фонові зображення) чи скрипт (зі стеком викликів). Size показує передано мережею і, сірим, фактичний розмір ресурсу; різниця між ними — це стиснення. Замість числа тут може стояти (memory cache) чи (disk cache), якщо ресурс узято з кешу без мережі. Time — загальна тривалість. Waterfall — смуга запиту на часовій шкалі; синя й червона вертикальні лінії позначають події DOMContentLoaded і load. Правий клік по заголовку таблиці додає колонки: Method, Protocol, Remote Address, Priority, будь-який заголовок відповіді.

Деталі запиту відкриваються кліком. Headers показує загальні відомості (URL, метод, статус, адресу сервера, Referrer Policy), заголовки відповіді й запиту з перемикачем Raw. Payload — параметри рядка запиту й тіло. Preview і Response — тіло відповіді у форматованому й сирому вигляді. Initiator — ланцюжок причин. Cookies — надіслані й отримані cookie. Timing розкладає час запиту на фази: Queueing і Stalled (очікування в черзі браузера), DNS Lookup, Initial connection, SSL, Request sent, Waiting for server response (час до першого байта відповіді) і Content Download.

Алгоритм діагностики зазвичай такий. Спершу знайдіть червоні рядки, тобто статуси 4xx і 5xx, і через Initiator з'ясуйте, хто їх запитав. Далі шукайте найдовші смуги в Waterfall і відкривайте їхній Timing. Довге Waiting for server response означає, що повільно працює сервер, і фронтенд тут не допоможе. Довге Content Download вказує на завеликий файл: перевірте Content-Encoding і розмір. Довгі Queueing чи Stalled свідчать, що запитів забагато або важливі ресурси мають низький пріоритет. Нарешті, повторіть завантаження й переконайтеся, що статичні файли беруться з кешу або повертають 304.

Контекстне меню запиту дає ще кілька інструментів. Copy → Copy as fetch чи Copy as cURL копіює запит як код, щоб відтворити його в консолі чи терміналі. Block request URL блокує ресурс, щоб перевірити, як сторінка переживе його відсутність. Експорт у HAR зберігає весь запис для колеги. Chrome типово експортує «очищений» HAR без cookie й заголовків авторизації, бо повний файл містить облікові дані, і пересилати його не можна.

// Result of "Copy as fetch" (shortened): the request can be replayed in Console
fetch("https://books.example.com/api/books?genre=css", {
  headers: { accept: "application/json" },
  method: "GET",
});

Коли це знадобиться. У кожній лабораторній, де щось завантажується. Потренуватися знаходити типові проблеми можна в тренажері панелі Network, а потім повторити те саме на справжньому сайті.

Хто творить вебстандарти

Вебом не володіє жодна компанія, а сайтом, зробленим двадцять років тому, мають змогу користуватися й сьогодні. Звідси три вимоги до правил: вони мають бути відкритими й безкоштовними для реалізації, однаково працювати в різних рушіях і не ламати наявні сайти. Принцип «не зламай веб» (don't break the web) — найсуворіше обмеження всіх вебстандартів. Тому їх пишуть кілька організацій, і кожна відповідає за свій шар.

IETF (Internet Engineering Task Force) розробляє протоколи інтернету: HTTP (RFC 9110–9114), TLS 1.3 (RFC 8446), QUIC (RFC 9000), cookie (RFC 6265 і його оновлення). Участь відкрита для всіх: робочі групи, як-от HTTP Working Group, працюють через публічні розсилки й репозиторії. Документ проходить шлях від чернетки Internet-Draft до RFC, а рішення ухвалюються за принципом «грубий консенсус і працюючий код».

W3C — консорціум, членами якого є компанії, університети й організації. Документ рухається за процесом W3C: робоча чернетка (Working Draft), кандидат у рекомендації (Candidate Recommendation), коли специфікація стабільна й чекає реалізацій, і рекомендація (Recommendation) після широкого обговорення та підтвердженого досвіду реалізації. Так розвиваються CSS, настанови доступності WCAG і багато Web API. Нові ідеї спершу інкубують у групах спільноти, зокрема WICG.

WHATWG веде Living Standards: HTML, DOM, Fetch, URL, Streams, Encoding, Console. Керівний комітет утворюють Apple, Google, Microsoft і Mozilla, але обговорення відкриті на GitHub. Зміна потрапляє в стандарт, коли її готові реалізувати щонайменше два рушії і немає вагомих заперечень, а супроводжують її тести. Двічі на рік WHATWG фіксує «знімок» стандарту (Review Draft) для юридичних патентних зобов'язань.

Ecma International, комітет TC39, розвиває ECMAScript (ECMA-262), а також API інтернаціоналізації ECMA-402. Формат JSON описано окремим стандартом Ecma — ECMA-404.

Хто ухвалює рішення насправді? Офіційно — консенсус учасників, але фактичне право вето мають ті, хто реалізує: специфікація, яку не реалізував жоден браузер, нічого не варта. Тому важливу роль відіграє спільна інфраструктура. web-platform-tests — спільний набір тестів для всіх рушіїв, результати якого публікує сайт wpt.fyi. test262 — набір тестів відповідності ECMAScript. Щорічний проєкт Interop — домовленість виробників браузерів разом виправити несумісності в обраних напрямах. А проєкт web-features групи W3C WebDX формує статус Baseline, який ви бачите на MDN.

Типовий шлях нової можливості такий. Спершу пишуть пояснювальний документ (explainer) з описом проблеми. Далі йде інкубація й обговорення, потім текст специфікації та реалізація «за прапорцем» або в обмеженому випробуванні. Після цього пишуть тести, можливість з'являється в кількох рушіях і нарешті отримує статус Baseline. Кожен може долучитися: відкрити issue в репозиторії специфікації, повідомити про баг у браузері чи прокоментувати пропозицію.

Коли це знадобиться. Щоб знати, де шукати відповідь «як це має працювати». Поведінка fetch описана у WHATWG Fetch, а не в ECMAScript; кешування — в RFC 9111; властивість CSS — у модулі специфікації CSS. А розбіжність між браузерами — привід перевірити wpt.fyi і трекер помилок, а не переписувати код навмання.

Як розвивається ECMAScript

Мові, якою пишуть мільярди сторінок, потрібно розвиватися, не ламаючи жодної з них, і однаково працювати в рушіях V8, SpiderMonkey і JavaScriptCore. Так було не завжди. JavaScript створив Брендан Айк у Netscape 1995 року за лічені тижні. 1996 року Netscape передав мову до Ecma, і 1997 року вийшов перший стандарт ECMAScript. Назва «JavaScript» є торговою маркою (нині її власник — Oracle), тож стандарт довелося назвати інакше.

Перші роки розвиток був ривками. ES3 (1999) додав регулярні вирази й try/catch. Амбітний ES4 обговорювали майже десятиліття й 2008 року відмовилися від нього через розбіжності. ES5 (2009) приніс суворий режим, вбудований JSON і методи масивів map, filter, reduce. Потім ES2015 (ES6) змінив мову сильніше, ніж усі попередні видання разом: let і const, стрілкові функції, класи, модулі, проміси, шаблонні рядки, деструктуризація. Готували його шість років. Висновок був очевидним, тож з 2016 року видання виходять щороку: усе, що готове на момент «зрізу» на початку року, Генеральна асамблея Ecma затверджує в червні. ECMAScript 2026, 17-те видання, затверджено 30 червня 2026 року.

Кожна можливість проходить процес TC39 стадіями. У кожної пропозиції є «чемпіон» — делегат, який її веде, а рішення про перехід ухвалюють консенсусом на пленарних зустрічах комітету, що відбуваються кілька разів на рік.

Stage 0 — ідея, ще не прийнята до розгляду. Stage 1 — комітет погоджується, що проблема варта розв'язання; є пояснення й приклади. Stage 2 — обрано бажаний підхід, з'явився чорновий текст специфікації. Stage 2.7 (введено 2024 року) — специфікацію завершено й схвалено в принципі, пишуть тести. Stage 3 — тести в test262 готові, рушії реалізують можливість, змінити її може лише досвід реалізації. Stage 4 — є щонайменше дві сумісні реалізації, які проходять тести, і текст вливається в чернетку специфікації, тобто можливість увійде до наступного щорічного видання.

Принцип «не зламай веб» тут видно особливо добре. 2018 року метод для «сплющування» масивів мав називатися flatten, але виявилося, що популярна колись бібліотека MooTools додає власний несумісний Array.prototype.flatten, і старі сайти зламалися б. Метод перейменували на flat. Із тієї самої причини вже ніколи не виправлять typeof null === "object": помилку 1995 року збережено, бо від неї залежить наявний код.

Для розробника з цього випливають прості правила. Те, що можливість є в стандарті, ще не означає підтримку в браузерах користувачів, тож перевірте MDN і Baseline. Stage 3 означає «скоро, але ще не всюди», Stage 2 і нижче — експеримент, який може змінитися до невпізнання. Новий синтаксис можна писати й для старіших браузерів: компілятор (наприклад, TypeScript, з яким ви працюватимете в цьому курсі) перетворить його на старіший еквівалент. Нові вбудовані функції він не додасть, тому їх перевіряють наявністю.

function canSumPrecisely() {
  return typeof Math.sumPrecise === "function"; // ES2026
}

function sumPrices(prices) {
  if (canSumPrecisely()) {
    return Math.sumPrecise(prices);
  }
  return prices.reduce((total, price) => total + price, 0);
}

console.log(sumPrices([0.1, 0.2, 0.3])); // 0.6 with ES2026 support, otherwise 0.6000000000000001

Коли це знадобиться. Коли стаття пропонує «новий метод», а в браузері його немає. Коли треба зрозуміти, чи безпечно брати можливість у проєкт. Коли читаєте код і бачите синтаксис, якого не було в підручнику. Що з'являлося в кожному виданні, показує інтерактивна хронологія.

Інтерактивне демо

Чотири тренажери працюють без мережі: сервер, кеш і панель Network змодельовано прямо на сторінці, тож експериментувати можна скільки завгодно.

HTTP-клієнт і тестовий сервер

Складіть запит до API каталогу й подивіться, що поверне сервер. Сервер зберігає зміни, поки сторінку відкрито. Спробуйте створити книжку без авторизації, видалити ту саму книжку двічі, надіслати зламаний JSON або повторити GET з If-None-Match.

Сервер знає маршрути /api/books і /api/books/{id}.

    Антипатерни

    Більшість цих помилок не дає явного збою на вашому комп'ютері. Вони проявляються пізніше: у кеші, у пошукового робота, на повільному з'єднанні або в іншого користувача.

    Змінювати дані запитом GET

    ✗ Погано 
    <a href="/api/books/2/delete">Delete book</a>

    Чому це погано. GET за специфікацією безпечний, і на це покладається вся інфраструктура. Пошуковий робот обійде посилання й видалить книжки. Браузер чи розширення можуть попередньо завантажити адресу, месенджер — запитати її для прев'ю. Проміжний кеш може зберегти відповідь «видалено». До того ж адреса з дією осідає в історії браузера й журналах сервера.

    ✓ Добре 
    async function deleteBook(id) {
  const response = await fetch(`/api/books/${id}`, { method: "DELETE" });
  return response.status === 204;
}

    Повертати 200 OK з помилкою в тілі

    ✗ Погано 
    HTTP/1.1 200 OK
Content-Type: application/json

{"error": "Book not found"}

    Чому це погано. Для всієї інфраструктури це успіх. Кеш збереже «помилку» як звичайну відповідь, response.ok дорівнюватиме true, панель Network не підсвітить рядок червоним, а моніторинг не помітить, що половина запитів невдала. Кожен клієнт мусить розбирати тіло, щоб зрозуміти, що сталося.

    ✓ Добре 
    HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"type": "about:blank", "title": "Not Found", "status": 404,
 "detail": "Book 42 does not exist"}

    Формат application/problem+json описано в RFC 9457: машинозчитуваний код стану плюс зрозумілі людині деталі.

    Неправильний Content-Type

    ✗ Погано 
    GET /js/app.js
HTTP/1.1 200 OK
Content-Type: text/plain
X-Content-Type-Options: nosniff

    Чому це погано. Браузер вирішує, що робити з тілом, за Content-Type, а не за розширенням файлу. Із nosniff він відмовиться виконувати «текстовий» скрипт, і застосунок не запуститься. Без nosniff браузер почне вгадувати тип, а це вже вразливість: завантажений користувачем «текстовий» файл може бути виконано як скрипт.

    ✓ Добре 
    HTTP/1.1 200 OK
Content-Type: text/javascript; charset=utf-8
X-Content-Type-Options: nosniff

    Довгий max-age для файлу під незмінним ім'ям

    ✗ Погано 
    GET /css/main.css
HTTP/1.1 200 OK
Cache-Control: max-age=2592000

    Чому це погано. Поки копія свіжа, браузер узагалі не звертається до сервера, тож про новий файл не дізнається. Після оновлення сайту відвідувачі ще до 30 днів бачать новий HTML зі старими стилями, і верстка ламається. Виправити це з сервера неможливо: відкликати копію з чужого кешу не можна.

    ✓ Добре 
    <!-- index.html: Cache-Control: no-cache -->
<link rel="stylesheet" href="/css/main.3f9a2c.css">
<!-- main.3f9a2c.css: Cache-Control: max-age=31536000, immutable -->

    Вважати, що no-cache забороняє кешування

    ✗ Погано 
    GET /api/profile
HTTP/1.1 200 OK
Cache-Control: no-cache

{"name": "Reader", "email": "reader@example.com", "card": "**** 4417"}

    Чому це погано. no-cache дозволяє зберегти відповідь на диск і лише вимагає перевіряти її перед використанням. Персональні дані лишаються в кеші браузера на спільному комп'ютері, а без private їх може зберегти й проміжний кеш.

    ✓ Добре 
    HTTP/1.1 200 OK
Cache-Control: no-store

    Чекати, що fetch кине помилку на 404 чи 500

    ✗ Погано 
    async function loadBooks() {
  try {
    const response = await fetch("/api/books");
    return await response.json();
  } catch {
    return []; // "handles" errors
  }
}

    Чому це погано. Якщо сервер відповів 500 зі сторінкою помилки в HTML, fetch завершиться успішно, а response.json() впаде на розборі HTML. catch поверне порожній список, і користувач побачить «книжок немає» замість повідомлення про збій. Справжня причина зникне, і налагодження перетвориться на здогадки.

    ✓ Добре 
    async function loadBooks() {
  const response = await fetch("/api/books");
  if (!response.ok) {
    throw new Error(`Books were not loaded: HTTP ${response.status}`);
  }
  return response.json();
}

    Передавати токени й персональні дані в URL

    ✗ Погано 
    GET /api/profile?token=eyJhbGciOi...&email=reader@example.com

    Чому це погано. HTTPS шифрує адресу в дорозі, але на кінцях вона зберігається відкрито: в історії браузера, журналах сервера й проксі, закладках, скріншотах, а частина адреси може піти в Referer на інший сайт. Токен із журналу дає повний доступ до облікового запису.

    ✓ Добре 
    GET /api/profile HTTP/1.1
Authorization: Bearer eyJhbGciOi...

    Ділитися повним HAR-файлом

    ✗ Погано 
    Network → Export HAR (with sensitive data) → attach to a public issue / chat

    Чому це погано. HAR — повний запис мережевої активності разом із cookie сесії, заголовками Authorization і тілами запитів. Будь-хто з файлом може увійти у ваш обліковий запис, доки сесія чинна. Такі витоки траплялися навіть у великих компаніях через файли, надіслані в службу підтримки.

    ✓ Добре 
    Network → Export HAR (sanitized)
or share: request URL, status, relevant headers, Timing screenshot

    Бест практики

    Правила, які роблять поведінку застосунку передбачуваною для браузера, кешів, інструментів і інших розробників.

    Обирати метод за семантикою

    Ресурси називають іменниками, а дію виражає метод. Тоді кешування, повторні запити, попереднє завантаження й документація працюють «самі», бо всі учасники розуміють намір однаково.

    GET    /api/books        not  GET /api/getBooks
POST   /api/books        not  POST /api/books/create
DELETE /api/books/2      not  GET /api/books/2/delete

    Точні коди стану й зрозуміле тіло помилки

    Клієнтський код розгалужується за кодом стану, а людина читає деталі. 201 з Location після створення, 204 після видалення, 422 з переліком полів, що не пройшли перевірку, 401 чи 403 залежно від того, чи знає сервер користувача.

    function getErrorMessage(status) {
  const messages = {
    401: "Увійдіть, щоб продовжити",
    403: "Недостатньо прав для цієї дії",
    404: "Книжку не знайдено",
    422: "Перевірте заповнені поля",
  };
  return messages[status] ?? `Сталася помилка (HTTP ${status})`;
}

    Явна стратегія кешування для кожного типу ресурсу

    Без Cache-Control браузер вмикає евристику, і поведінка стає непередбачуваною. Явні правила за типом ресурсу дають і швидкість, і миттєві оновлення після деплою.

    HTML documents         Cache-Control: no-cache            + ETag
Hashed static files    Cache-Control: max-age=31536000, immutable
Public API lists       Cache-Control: max-age=60          + ETag
Personal API data      Cache-Control: private, no-cache   + ETag
Sensitive data         Cache-Control: no-store

    Валідатори для дешевих повторних перевірок

    ETag перетворює перевірку актуальності на відповідь 304 у кількасот байтів замість повного файлу. Це особливо помітно на мобільних мережах, де дорогий кожен кілобайт, а не лише кожна секунда.

    GET /api/books HTTP/1.1
If-None-Match: "v8"

HTTP/1.1 304 Not Modified
ETag: "v8"

    Стиснення і правильні типи для текстових ресурсів

    HTML, CSS, JavaScript, JSON і SVG добре стискаються: Brotli чи gzip зменшують їх у кілька разів. Браузер сам оголошує підтримувані алгоритми в Accept-Encoding і сам розпаковує відповідь. У Network це видно за різницею двох чисел у колонці Size. Правильний Content-Type разом із nosniff гарантує, що браузер не вгадуватиме тип.

    HTTP/1.1 200 OK
Content-Type: text/css; charset=utf-8
Content-Encoding: br
Vary: Accept-Encoding
X-Content-Type-Options: nosniff

    Розрізняти помилку мережі й помилку HTTP

    Це різні ситуації з різною реакцією. Немає мережі — варто запропонувати повторити спробу. 401 — попросити увійти. 500 — повідомити про збій. Окрема перевірка response.ok і окремий catch роблять цю різницю явною.

    async function requestBooks() {
  try {
    const response = await fetch("/api/books");
    return { ok: response.ok, status: response.status, data: response.ok ? await response.json() : null };
  } catch {
    return { ok: false, status: 0, data: null }; // network error: no response at all
  }
}

    Діагностувати мережу за алгоритмом

    Послідовність кроків захищає від хибних висновків: від «у мене швидко» (бо працює кеш і швидка мережа) до виправлення фронтенду, коли повільно відповідає сервер.

    1. Network → Disable cache, Preserve log → reload
2. Filter: status-code:404 / -status-code:200 → red rows → Initiator
3. Longest Waterfall bars → Timing: Waiting (server) or Download (size)
4. Throttling: Slow 4G → does the page stay usable?
5. Uncheck Disable cache → reload → static files from cache or 304?

    Перевіряти нові можливості за першоджерелами

    Статті застарівають, а стадія пропозиції чи підтримка в браузерах змінюється щомісяця. MDN зі статусом Baseline, специфікація й таблиці сумісності дають актуальну картину, а перевірка наявності в коді захищає користувачів старіших браузерів.

    function supportsSetMethods() {
  return typeof Set.prototype.union === "function"; // ES2025
}

    Квіз для самоперевірки

    Запитання перевіряють розуміння механізмів, а не визначення. Після кожної відповіді з'явиться пояснення; прогрес зберігається в цьому браузері.
